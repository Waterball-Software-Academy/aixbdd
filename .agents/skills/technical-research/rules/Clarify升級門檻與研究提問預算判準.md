# Rule 1 - 只有會改變研究結論的高影響缺口才應升級到 `/clarify`

- Level: `MUST`
- 只有當缺口會改變決策集合、候選方案邊界、比較維度、不可違反限制、推薦方向或後續 handoff 判斷時，才應升級到 `/clarify`。
- 若未定細節只影響文字表述、次要比較角度、例句內容或可在 `Rationale` 中明示保留的局部假設，不應直接升級到 `/clarify`。
- 不可把所有研究不確定性都轉成訪談，讓上游 skill 失去先行收斂研究問題的責任。

## Good Example

- 這個例子是好的，因為它只把會改變推薦方案的缺口升級為 clarify。

````md
研究主題：照片日期相簿整理的圖片儲存策略。

高影響缺口：
- 第一版是否允許把原圖存放在檔案系統而非資料庫
- 是否存在必須支援的離線備份限制

決策：
- 升級到 `/clarify`
````

## Bad Example

- 這個例子是壞的，因為它把局部 wording 也升級為 clarify。

````md
研究主題：照片日期相簿整理的圖片儲存策略。

低影響細節：
- 標題要寫「研究」還是「技術研究」
- Alternatives considered 要列 2 個還是 3 個

決策：
- 升級到 `/clarify`
````

# Rule 2 - 每輪 research clarify 只處理最高影響的 1 至 3 題

- Level: `MUST`
- `technical-research` 在委派 `/clarify` 前，必須先自行排序研究缺口，只把本輪最高影響的 1 至 3 題交給 `/clarify`。
- 若高影響缺口超過 3 題，應保留最關鍵的 1 至 3 題先問，其餘風險可留在 artifact 中揭露或待下一輪。
- 不可把未整理的一長串技術問題原樣傾倒給 `/clarify`。

## Good Example

- 這個例子是好的，因為它先排序，再只問最影響研究方向的問題。

````md
本輪缺口排序：
1. 第一版允許的部署邊界
2. 是否必須支援多租戶
3. 資料保留政策
4. 文件標題命名偏好

委派：
- 本輪只把前 3 題交給 `/clarify`
````

## Bad Example

- 這個例子是壞的，因為它把大小不一的問題一次全部丟出。

````md
委派：
- 把 9 題技術疑問全部交給 `/clarify`
````

# Rule 3 - 低風險未定細節應保留在研究內容中明示

- Level: `MUST`
- 若主要決策、比較維度與推薦方向已可成立，但仍有少數局部資訊未定，應優先在對應決策的 `Rationale` 或 `Alternatives considered` 中明示假設、限制或待驗證點。
- 只有當未定細節已影響最終採納結論或下一步 handoff，才應升級回 `/clarify`。
- 不可為了追求文件表面完整，就對每個局部未知都發起訪談。

## Good Example

- 這個例子是好的，因為它保留局部不確定性，但不阻塞主要研究結論。

````md
- **Rationale**: 採用資料庫 BLOB 可維持交易一致性；實際容量上限仍需在實作階段以驗收資料集做壓力驗證。
````

## Bad Example

- 這個例子是壞的，因為它把可保留的局部驗證點也升級為中斷性提問。

````md
缺口：
- 還不知道單張圖片平均大小會是 4MB 還是 5MB

決策：
- 暫停 research，立刻進 `/clarify`
````

# Rule 4 - 產品範圍已拍板的不得重問；BDD techstack、測試策略、系統有哪些端不算在內

- Level: `SHOULD`
- 當 `/specify` 已在 `spec.md` 中明確拍板產品功能邊界、第一版做／不做、成功標準或業務限制時，`technical-research` 應直接沿用，不應把同一產品問題再次交給 `/clarify`。
- 下列三題即使 `spec.md` 假設或範圍已經寫了答案，仍必須依 `rules/AIxBDD必問問題與起始專案介面澄清判準.md` 處理，不得用本條跳過：
  - BDD techstack
  - 測試策略
  - 起始專案時系統有哪些端
- `spec.md` 寫「純前端」「無後端」「無資料庫」「不要 E2E」，只代表產品草稿假設，不代表這三題已拍板。
- 只有在使用者最新指示與 `spec.md` 的產品範圍互相衝突，或產品範圍本身仍未定時，才應重問產品題。

## Good Example

- 這個例子是好的，因為產品範圍沿用 spec，三題必問題仍 clarify。

````md
已知 `spec.md` 已明確寫出：
- 第一版只做單層日期相簿
- 假設：本版無後端

決策：
- 相簿層數沿用 spec，不再次發問
- 仍要 clarify BDD techstack、測試策略、系統有哪些端
````

## Bad Example

- 這個例子是壞的，因為它用 spec 假設跳過必問題。

````md
已知 `spec.md` 已明確寫出：
- 假設：本版無後端、不要 E2E

決策：
- 沿用純前端，不問有哪些端
- 沿用 vitest，不問測試策略與 BDD techstack
````
