# Rule 1 - 澄清答案必須寫回最具責任歸屬的 section

- Level: `MUST`
- 每個已確認答案都必須寫回最能承接其語意責任的 spec section，不可只追加在統一的備註區或會議紀錄區。
- 回寫位置至少依下列對應收斂：
  - 故事邊界、角色差異、主要流程改變：更新對應 `使用者故事`、其敘述、優先級理由或驗收情境
  - 故事專屬功能需求：更新該故事底下的 `功能需求（FR）`
  - 故事專屬非功能需求：更新該故事底下的 `非功能需求（NFR）`
  - 跨故事規則或全域限制：更新 `全域需求`
  - 錯誤處理、負向情境、斷線、衝突解法：更新 `邊界情況`
  - 關鍵名詞、實體欄位、關係、狀態：約束更新 `關鍵實體` 或對應故事內容
  - 可量測門檻、驗收完成條件：更新 `成功標準`
  - 僅屬前提與邊界的未定事項：更新 `假設` 或保留為明示 deferred 風險
- 若答案會同時影響多個 section，應更新所有受影響 section，但每個 section 只承接自己應有的責任，不重複貼同一段話。

## Good Example

- 這個例子是好的，因為它把答案寫回正確 section，而不是只留在補充紀錄。

```md
澄清答案：
- 對戰先手採隨機決定

回寫：
- 更新使用者故事 3 的驗收情境
- 更新對應 FR 中的先手規則
- 必要時補一條成功標準驗證先手分配
```

## Bad Example

- 這個例子是壞的，因為它沒有把答案整合回規格責任區。

```md
澄清答案：
- 對戰先手採隨機決定

回寫：
- 只在文件最下方加一行「補充：先手是隨機」
```

# Rule 2 - 若新答案推翻舊敘述，必須替換或刪除舊內容，不可並存

- Level: `MUST`
- 若本輪澄清答案與原 spec 既有敘述衝突，必須以新答案取代舊敘述，或刪除被推翻的文字，不可讓互相矛盾的說法並存。
- 不可用「另外補充」的方式把新答案疊在舊內容旁邊，讓後續執行者自己猜哪個版本才有效。
- 若衝突橫跨多個 section，必須逐一清理所有受影響處，而不是只修一處。
- 若本輪答案尚未完全定案，只能保留一個明確的暫時狀態，不可同時保留兩種互斥選項。

## Good Example

- 這個例子是好的，因為它清掉被推翻的描述，讓規格只有一個有效版本。

```md
原文：
- 房主先手 [NEEDS CLARIFICATION]

澄清答案：
- 先手改為隨機決定

處理：
- 刪除原本「房主先手」表述
- 改成「系統 MUST 在對戰開始時隨機決定首位出牌玩家」
```

## Bad Example

- 這個例子是壞的，因為它把互斥結論並存，讓規格更亂。

```md
原文保留：
- 房主先手

另外補充：
- 澄清後改成隨機先手
```

# Rule 3 - 術語必須統一到 canonical 名稱，避免同義漂移

- Level: `SHOULD`
- 若澄清後發現 spec 對同一概念使用多種名稱，應選定一個 canonical term，並在受影響 section 中統一用語。
- 只有在保留舊稱有助於過渡理解時，才可在首次出現處補一個「原先稱作 X」的對照，不可整份文件來回混用。
- 術語統一範圍至少包括使用者故事、FR/NFR、邊界情況、關鍵實體與成功標準。

## Good Example

- 這個例子是好的，因為它選定單一術語並一致回寫。

```md
觀察：
- 同一概念同時被寫成「房間碼」、「配對碼」與「進房碼」

處理：
- 統一為「配對碼」
- 必要時首次出現補註「原先稱作房間碼」
```

## Bad Example

- 這個例子是壞的，因為它接受答案後仍讓多種名稱平行存在。

```md
處理：
- 使用者故事保留「房間碼」
- FR 改成「配對碼」
- 成功標準寫「進房碼」
```

# Rule 4 - 未解高影響缺口要明示保留狀態，不可用腦補補洞

- Level: `MUST`
- 若本輪 `/clarify` 後仍有高影響缺口未解，必須在 spec 或完成回報中明示其當前狀態，例如 `NEEDS CLARIFICATION`、deferred 風險、或需交由後續 skill 判定。
- 不可因為想讓文件看起來完整，就自行補上一個未經確認的答案。
- 若某缺口已明確 defer 到後續研究、plan 或實作設計，應寫出 defer 理由，讓後續 skill 知道這不是遺漏，而是刻意保留。

## Good Example

- 這個例子是好的，因為它保留真實未定狀態，而不是假裝已拍板。

```md
狀態：
- 斷線後是暫停、判負或等待重連仍未定

處理：
- 在邊界情況中保留 `NEEDS CLARIFICATION`
- 在完成回報中明示此缺口仍阻塞 readiness
```

## Bad Example

- 這個例子是壞的，因為它在沒有確認時擅自補完答案。

```md
狀態：
- 斷線規則尚未確認

處理：
- 為了讓 spec 完整，直接寫成「30 秒未重連即判負」
```
