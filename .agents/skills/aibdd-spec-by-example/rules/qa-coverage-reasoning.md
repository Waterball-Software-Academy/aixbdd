# QA 覆蓋推導（Reasoning Flow）

補完各 rule 的第一份 pattern Example 後，用 QA 視角把該測的情境想全、增補遺漏案例。原則：需求明文（`$QUOTE_SEGMENTS`）的必須覆蓋；需求未明文的不發明，拿不準走 `$ASK_BATCH` 交 clarify。

## 增補原則：只提供關鍵參數變化

增補的 example 只讓被測的關鍵參數以具體值變化，其餘沿用同 rule 既有例子的寫法與預設，不重複鋪陳整份資料。讀者兩句對照就該看出「這一例在變什麼」：

```gherkin

# 測試設計註記：上限 200 萬的 BVA 對照（max / max+1）
Example: 目標額度等於上限 200 萬，提交成功
  When "Alice" 提交目標額度 2000000 的試用單

Example: 目標額度超過上限，提交沒有成功
  When "Alice" 提交目標額度 2000001 的試用單
```

（註解之前必為空行——`formatter-rules.md` 的註解空行規則適用於**所有** Example 上方註解，
含 `# 取捨：` 與 `# 測試設計註記`。）

## 推情境：對每條 rule 問一輪覆蓋問題

問參數——每個輸入壞掉會怎樣？

- 等價類：每個輸入參數，有效類至少一例、每個無效類（缺漏、格式錯、允許值以外）至少一例；允許值清單類參數至少要有「清單外的值」一例。
- 邊界值：需求明文的值域必掃邊界內外（max 與 max+1 對照）；未明文的禁止發明邊界。

問 rule 本身——照做會過、不照做會擋，都證明了嗎？

- 正例反例：每條 rule 至少一個正例與一個反例；只寫快樂路徑不算覆蓋。**例外（失敗型 rule）**：pattern A（前置（參數））與 pattern B（前置（狀態））依 `rule-pattern-taxonomy.md` 鎖定為失敗語意，把「成功」例掛在它們底下會違反 pattern lock。故 **A／B 的 rule 只需反例，其正例由同一 feature 的 pattern C／D rule 的成功例承擔**——C／D 的成功例本來就走完了 A／B 的前置檢查，即是它們的正例。
  - 「權限四面」的歸屬同此原則講明：**無權拒絕／未認證拒絕／跨資源拒絕**三面掛在 `前置（狀態）` 的權限 rule（pattern B）下；**有權成功**那一面掛在同 feature 的 `後置（狀態）`／`後置（回應）` rule（pattern C／D）——該例的操作者本來就是有權角色，不另立正例、也不掛回權限 rule。
- 不可漏場景：失敗嚴重度是 漏寫 > 亂編 > 一個場景混多件事；漏掉的場景不會紅燈，比寫錯更危險。
- 多條件 rule：每個條件至少要有「唯獨它不成立」的一例，只驗全真組合不夠。

問狀態——實體有狀態機嗎？每個合法轉移至少一例；每個狀態至少驗一個代表性非法轉移（預期錯誤＋狀態未變更）。

問實體——CRUD 四面都有著落嗎？缺面要能指回需求說明為何不適用；寫入類操作至少一例走「寫後讀」驗查詢端一致。

問查詢的形狀——列表自己的行為測了嗎？需求明文有排序或分頁時：排序至少一個多筆資料的例子斷言順序；分頁至少覆蓋跨頁與超出頁數；零筆結果至少一例斷言「仍成功、列表沒有內容」。列表關鍵情況要寫滿：多筆（含排序決策）、空列表、他人資料隔離——缺哪個要說得出被哪條 rule 涵蓋，不能是沒想到。

問重送——第二次來會怎樣？唯一性約束至少一個「重複值第二次提交」的反例；可重試操作至少一個重送例，斷言結果冪等。

問權限——換個人來會怎樣？受保護操作四面：有權成功、無權拒絕、未認證拒絕、跨資源拒絕（水平越權最常被漏想）；後三者同時驗狀態未變更。需求無權限語意可豁免，但要能指回需求。

問失敗與副作用——失敗之後、成功之外，系統還動了什麼？

- 失敗情境除失敗結果外，還要有一條資料層驗證：資料不存在或維持原值；刪除成功要驗資料真的不在了。
- 需求明文的對外效應（通知、稽核、外部呼叫）要有例子斷言效應確實發生；未明文的不發明。
- 狀態變更操作不能只驗回應成功，至少一例驗資料落庫成正確狀態。

## 對矩陣：收斂檢查

- 一例一焦點：每條 rule 至少一個 example；每個 example 只驗一條 rule 的一個面向，失敗時才定位得出誰破了。
- 不跑題：每個 example 先問「它在驗所屬 rule 的哪一面？」跑題或漏條件即重擬。
- 不重複：同 rule 下語意重複的 example（標題近似、步驟雷同，或一窄一寬而窄者無獨立價值）保留最完整的一份；已有 Example 的 rule 不重複補。
