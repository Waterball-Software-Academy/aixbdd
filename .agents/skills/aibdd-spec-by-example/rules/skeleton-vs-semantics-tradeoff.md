# 骨架 vs 業務語意 取捨守則

- pattern 模板必為「最大集合」骨架；實際 Example 得為其子集，不必每個 placeholder 都填。
- 省略骨架元素僅當該元素在此 case 重複或無業務區別力；禁止為了少寫而省略仍有意義之元素。
- 省略時必須在 Example 上方加註解 `# 取捨：<原因>`；不得省略卻不留註解。
- 取捨決策僅當在草擬 Example 時執行；其他步驟不得自作主張省略元素。

## 觸發省略的三種情境

- 兩個骨架元素指向同一觸發動作（例：Command 與 Query 在此 case 為同一動作）: 省略 Given 中重複的那個
- 骨架元素在此 case 無業務區別力（例：Actor 在所有 Example 都一樣）: 可省，但建議只在 Background 集中表達
- 骨架元素於此 case 必為「無」（例：前置失敗的 Event）: 省略，模板本就不應出現

## Good

- Feature `結帳套用優惠券`、PATTERN_A：Given 骨架要求列 `<Command>`（執行結帳），但 When 也是「執行結帳」 → 省略 Given 的 Command，加註解 `# 取捨：Command 與觸發動作為同一事件（執行結帳），故 Given 不重複列`。
- PATTERN_B：Event 在前置失敗為「無」，骨架本就不列；不需要寫註解。

## Bad

- 為了 Example 簡潔，省略 PATTERN_A 的 Input：失敗原因消失，讀者看不出為何失敗；禁止省略 Input。
- 省略 Command／Query 卻不加註解：未來讀者無法判斷是漏寫還是有意取捨；必須註解原因。
- PATTERN_C 在**系統有事件機制**時省略 Event：後置成功的事件必為驗證核心，省略即破壞 pattern 語意；禁止省略。（需求明文排除通知機制時另有例外，見下節。）
- 在 5 元素推導時就決定省略：取捨僅當在草擬 Example 時執行，否則 5 元素檢核會少資料。

## PATTERN_C 的 Event 例外：需求明文排除通知／事件機制

pattern C 無條件要求每個成功 Example 都斷言 `系統發出 "<業務化通知名>"`。當**需求明文排除**
任何通知／事件機制時（例：PRD 明列「本期不做 App 推播、不做 Email 通知」），這條要求會系統性
逼出需求沒授權的內容——不省略就得自生一個通知名，那違反「禁止自生」。

判準：**需求明文排除**才適用（`$QUOTE_SEGMENTS` 裡找得到那句排除條文）；只是「需求沒提到通知」
不算——沒提到就走 `$ASK_BATCH` 交 clarify，不得自行認定為排除。

成立時，依序擇一（優先序即列出順序）：

1. **以「操作者可見的完成回饋」表達 Event**（首選）：把 Event 落成操作者當下就看得到的完成語意
   （`Then "林小柔" 看到會員建立完成`／`會籍生效完成`），它是真實可觀測的業務結果，不是自生的通知機制。
2. **省略 Event**：1 也表達不出來（連完成回饋都不存在）時才省略，並依本檔通則在 Example 上方加
   `# 取捨：需求明文排除通知機制（<指回排除條文>），本例無 Event`。

無論選 1 或 2，都**必須**把需求的排除條文寫進 `${PLAN_SPEC}` 的澄清紀錄留痕（batch `$BATCH_NO`、
owner `aibdd-spec-by-example`），讓下游知道這不是漏寫。
