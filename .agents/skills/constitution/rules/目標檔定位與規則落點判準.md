# Rule 1 - 根憲法只承接治理邊界，不承接 artifact 細則

- Level: `MUST`
- `CONSTITUTION.md` 只負責定義治理原則、讀取順序、目錄約定與規則格式邊界。
- 若需求是在描述某個 skill 的某個 artifact 應具備什麼欄位、語意、禁止事項或 example，
  不得寫進 `CONSTITUTION.md`。
- 若把 artifact 細則寫進根憲法，會讓根檔快速膨脹，破壞模組化設計。

## Good Example

- 這個例子是好的，因為根憲法只保留治理層資訊。

````md
### V. 目錄只保留真正會被讀的規則

1. `CONSTITUTION.md`
2. `shared.md`
3. `skills/<current-skill>/<artifact>.md`
````

## Bad Example

- 這個例子是壞的，因為它把 API response 細節直接塞進根憲法。

````md
### VI. API Response Rules

- 所有 `200` response 都必須包含 `roomId`
- 所有 `409` response 都必須包含 `errorCode`
````

# Rule 2 - 只有真正跨 skill 的規則才寫入 shared.md

- Level: `MUST`
- `shared.md` 只能收錄跨多個 skill 與多種 artifact 都會重複使用的規則。
- 若某條規則其實只服務單一 skill 或單一 artifact，應寫進 `skills/<skill>/<artifact>.md`。
- 判斷時以「誰會直接消費這條規則」為準，而不是以規則主題看起來是否通用為準。

## Good Example

- 這個例子是好的，因為語言一致性會被多種 artifact 共同使用。

````md
## Rule 1 - 說明文字必須使用繁體中文
````

## Bad Example

- 這個例子是壞的，因為 API response 其實只會由 `/api-plan` 的 contract artifact 使用。

````md
## Rule 2 - 成功與失敗回應必須分流表達
````

# Rule 3 - skill 規則檔以 artifact 為最小落點

- Level: `MUST`
- `skills/<skill>/` 底下每一個 `.md` 檔都只處理單一 artifact。
- 若同一 skill 會產出 `spec.md` 與 `requirements-checklist.md`，應拆成兩個檔案，而不是混寫。
- 只有當兩條規則同時約束同一個 artifact 時，才應放在同一檔案中。

## Good Example

- 這個例子是好的，因為 skill 目錄下每個檔只對應一個 artifact。

````text
skills/specify/spec.md
skills/specify/requirements-checklist.md
````

## Bad Example

- 這個例子是壞的，因為不同 artifact 的規則被混在同一份檔案中。

````text
skills/specify/constitution.md
# 內含 spec 與 requirements-checklist 的全部規則
````
