# Rule 1 - 只有會改變落點或強度的缺口才升級訪談

- Level: `MUST`
- 只有當缺口會改變規則應寫到哪個檔、是否需要新增檔案、規則強度應為 `MUST` /
  `SHOULD` / `MAY`，或會改變規則本體內容時，才應升級為訪談問題。
- 若使用者已經明示規則主題、目標 skill 與 artifact，則不應再重問低價值問題。
- 不得為了追求完整而訪談所有小細節；本 skill 只處理本次必要的高影響缺口。

## Good Example

- 這個例子是好的，因為它只問真正會影響規則落點與強度的問題。

````md
Q1: 這條 API response 規則要掛在 `shared.md`，還是 `skills/api-plan/openapi.md`？
Q2: 這條規則是硬性 `MUST`，還是可帶理由偏離的 `SHOULD`？
````

## Bad Example

- 這個例子是壞的，因為它把不影響憲法落點的語氣偏好也升級成正式訪談。

````md
Q1: 這條規則標題要不要更口語？
Q2: Good Example 要不要用兩個空行？
````

# Rule 2 - 每輪只問最小必要題數

- Level: `MUST`
- 每一輪 clarify 應只問 1 至 3 題，並優先處理最能避免錯放規則或過度擴張的缺口。
- 若第一輪回答後已足以落檔，應停止續問，不得為了湊題數而追加問題。
- 若問題之間存在前後依賴，應先問上游問題，再決定是否需要後續提問。

## Good Example

- 這個例子是好的，因為它先確認是否應該新建檔，再決定是否有必要追問細節。

````md
Q1: 這條規則是新增到既有 `skills/tasks/tasks.md`，還是新建 skill artifact 檔？
Q2: 若新建檔，目標 artifact 名稱是什麼？
````

## Bad Example

- 這個例子是壞的，因為它在還沒確認目標檔之前，就一次展開太多下游細節。

````md
Q1: 規則標題是什麼？
Q2: Good Example 要幾個？
Q3: Bad Example 要不要含 code block？
Q4: 檔名英文還中文？
Q5: 是否加入補充備註？
````

# Rule 3 - 訪談完成後必須能直接回到最小寫入集合

- Level: `SHOULD`
- 訪談結束後，回答結果應能直接映射到「修改哪幾個檔、每個檔新增什麼規則」。
- 若問題設計無法導回具體檔案與規則內容，表示提問過度抽象，應重寫問題。

## Good Example

- 這個例子是好的，因為回答後能直接決定落點與修改面。

````md
回答：
- 掛在 `skills/data-plan/data-model.md`
- 強度為 `MUST`

後續寫入：
- 只修改一個檔案
- 在檔內新增一條 Rule
````

## Bad Example

- 這個例子是壞的，因為回答完仍然不知道要改哪個檔案。

````md
回答：
- 想要更嚴謹一點
- 感覺偏資料面
````
