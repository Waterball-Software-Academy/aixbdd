# Rule 1 - 預設只修改已存在的最小檔案集合

- Level: `MUST`
- 若需求可以透過修改既有 `CONSTITUTION.md`、`shared.md` 或單一 `skills/<skill>/<artifact>.md`
  完成，則不得額外新增第二個規則檔或旁枝說明檔。
- 只有當需求明確新增新的 skill artifact 落點時，才應建立新的 `.md` 檔。
- 不得因為主題相近就順手重寫其他 skill 的規則檔。

## Good Example

- 這個例子是好的，因為它只動到真正需要改的那個 artifact 規則檔。

````md
需求：補一條 `tasks.md` 的技術參照規則
結果：只修改 `skills/tasks/tasks.md`
````

## Bad Example

- 這個例子是壞的，因為需求只影響單一 artifact，卻額外建立一串新檔案。

````md
需求：補一條 `tasks.md` 的技術參照規則
結果：
- 新建 `shared-tasks.md`
- 新建 `tasks-reference.md`
- 重寫 `CONSTITUTION.md`
````

# Rule 2 - 新規則只寫支撐本次需求的必要內容

- Level: `MUST`
- 每次新增的規則只應覆蓋本次需求真正需要的判斷面，不得順勢擴張成完整治理章程。
- 若某個延伸面向尚未被使用者要求，應保留為未來增量，而不是預先一次寫滿。
- Good / Bad Example 也應只示範本條規則的核心差異，不延伸到其他未要求主題。

## Good Example

- 這個例子是好的，因為它只補上「response 分流」這個必要約束。

````md
## Rule 1 - 成功與失敗回應必須分流表達

- Level: `MUST`
- success response 與 error response 必須分開描述。
````

## Bad Example

- 這個例子是壞的，因為它趁機把認證、分頁、命名、版本治理全部一起寫進去。

````md
## Rule 1 - API 全域治理總表

- response 分流
- auth header
- cursor pagination
- versioning policy
- deprecation strategy
````

# Rule 3 - 覆寫時優先局部修正，不重寫整份檔案

- Level: `SHOULD`
- 若既有規則檔只有局部不足，應優先補強、改名或改寫局部段落，而不是整份重寫。
- 只有當既有檔案的責任邊界已經明顯錯誤時，才應考慮大幅重構。

## Good Example

- 這個例子是好的，因為它只補一條新 Rule，不干擾既有規則。

````md
原檔已有 Rule 1
本次只新增 Rule 2
````

## Bad Example

- 這個例子是壞的，因為它在沒有必要時整份重寫既有 artifact 規則檔。

````md
原檔已有 3 條穩定規則
本次因新增 1 條規則而整份全部改寫
````
