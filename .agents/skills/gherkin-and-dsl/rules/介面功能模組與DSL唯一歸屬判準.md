# Rule 1 - Feature 必須歸入既有功能模組

- Level: `MUST`
- 每個 feature file 必須位於 `{介面}/{模組}/*.feature`；`{介面}` 是 `backend`、`frontend` 等介面根，介面根目錄禁止直接放置 `.feature`。
- `模組` 必須優先依既有 truth 的功能邊界辨識，而不是依檔名方便、單次任務名稱或句型數量臨時切分。
- 只有既有功能邊界都無法合理承接時，才可新增模組；新增前必須說明新能力為何不屬於任何既有模組。
- 通用規則不得硬編碼某一個專案當下的模組清單；例如既有六個模組只能作為該專案的 truth，不可被寫成所有專案都必須採用的 taxonomy。

## Good Example

- 這個例子先沿用 truth 中已存在的「訂單」邊界，且 feature 位於介面根下一層模組。

```text
features/
└── backend/
    └── 訂單/
        └── 訂單提交重算.feature
```

## Bad Example

- 這個例子把 feature 留在介面根，並把特定專案的六個模組誤當成通用限制。

```text
features/backend/訂單提交重算.feature

規定：所有專案只能使用配對與房間、準備與密文、對戰回合、
三連猜、生命值與換密、房間聊天六個模組。
```

# Rule 2 - DSL row 依完整契約決定共用或專屬

- Level: `MUST`
- 只被單一模組使用，或只在單一模組語境中成立的 DSL 句型，必須放在 `{介面}/{模組}/dsl.md`。
- DSL row 只有在跨兩個以上模組使用，而且 `DSL 句型`、`Gherkin 參數`、`Data Table 參數`、`預設參數`、實作契約全部一致時，才可放在 `{介面}/dsl.md`。
- 任一參數型別、DataTable 欄位、預設值、權威狀態、等待條件、回寫或驗證責任不同，就不是同一份共用契約，必須留在各自模組並改成可辨識其語意的不同句型。
- 介面根 `dsl.md` 是跨模組契約，不是所有 DSL row 的總表，也不是先集中再視情況拆分的暫存區。

## Good Example

- 兩個模組使用完全相同的句型與契約，因此由介面根唯一承接。

```text
折扣/折扣碼套用.feature
  Given 購物車中已有以下商品：

訂單/訂單重算.feature
  Given 購物車中已有以下商品：

backend/dsl.md
  `購物車中已有以下商品：`
  DataTable、預設值、落地狀態與回寫契約在兩個模組完全相同。
```

## Bad Example

- 兩個模組雖使用相同文字，但一邊建立權威資料、一邊只驗畫面投影，實作契約不同，不能上提為共用 row。

```text
庫存模組：`商品庫存如下：` 代表寫入資料庫庫存。
商品頁模組：`商品庫存如下：` 代表驗證頁面顯示。

錯誤作法：只因句子相同，就合併到介面根 dsl.md。
```

# Rule 3 - 文字重複不能取代語意判斷

- Level: `MUST`
- 不得僅因 DSL 句型文字相同、搜尋到兩次，或看似可減少 row 數量，就把句型上提到介面根。
- 上提前必須逐欄比較句型、參數、DataTable、預設值與實作契約，並確認使用它的模組確實共享同一個業務動作或驗證責任。
- 同文異義的句型必須改寫成不同且可辨識的 DSL 句型；不可保留模糊同文，再要求 step definition 依所在 feature、標籤或呼叫順序猜測語意。
- 機械稽核可以指出重複、單一模組使用或匹配歧義，但不得代替 agent 決定兩份契約是否語意一致。

## Good Example

- 相同文字承載不同責任時，句型被拆成能直接表意的兩句。

```gherkin
Given 後端庫存已設定如下：
Then 商品頁顯示庫存如下：
```

## Bad Example

- 同一句依上下文切換 arrange 與 assertion，step definition 必須腦補所在模組。

```gherkin
Given 商品庫存如下：
Then 商品庫存如下：

# 只因文字出現兩次，就在介面根保留一個模糊的 `商品庫存如下：`。
```

# Rule 4 - 每個句型只能有一個權威位置

- Level: `MUST`
- 同一介面內，同一句型只能存在於一個權威 `dsl.md`；對任一 feature step 合併查找介面根與同模組 DSL 時，必須恰好命中一個 DSL row。
- 句型從模組升格到介面根時，必須移除所有模組中的舊 row；句型從介面根下放到模組時，必須移除根目錄舊 row。
- 不得以相容期、索引方便或避免搬移為由，在根與模組、或多個模組同時保留 duplicate row。
- 完成搬移後必須重新檢查所有使用該句型的 feature；若下放後仍被多個模組使用，應分別改寫成語意明確的句型，或在完整契約一致時維持根目錄唯一 row。

## Good Example

- 共用契約確認成立後，句型只保留在根目錄，兩個模組合併查找都各命中一次。

```text
backend/dsl.md
  `這次操作被拒絕`

backend/折扣/dsl.md
  （沒有此 row）

backend/訂單/dsl.md
  （沒有此 row）
```

## Bad Example

- 升格後沒有刪除舊位置，導致折扣 feature 合併查找時命中兩次。

```text
backend/dsl.md
  `這次操作被拒絕`

backend/折扣/dsl.md
  `這次操作被拒絕`
```
