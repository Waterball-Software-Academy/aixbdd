# Rule 1 - One-Shot 的一輪任務集恰好一個已解鎖 task

- Level: `MUST`
- One-Shot 每一輪執行的任務集必須恰好包含 1 個已解鎖且未完成的 task。
- 若當前 phase 有 `Parallel Hint`，本輪任務集改為 Hint 列出的 `[P]` 批次，不算跳步驟。
- 未標 `[P]` 的序列 task，即使都已解鎖，也不得併成同一輪實作。
- don't stop until deliver / One-Shot 不是跳步驟的許可。One-Shot 只代表完成當前任務集的驗證與回寫後，再重算下一個 task，不是把序列 task 併成同一輪。

## Good Example

- 這個例子是好的，因為 Phase 3 走 Hint 批次，Feature 仍單 task。

```md
Phase 3：本輪任務集 = {T008–T014}。
Phase 4：本輪任務集 = {T016 [BDD-GREEN]}。
```

## Bad Example

- 這個例子是壞的，因為把 Phase 3 與 Green 一次打包。

```md
agent 決定本輪一次做完 T008–T016，最後再一起打勾。
```

# Rule 2 - 下列行為一律視為跳步驟，嚴格禁止

- Level: `MUST`
- 執行 `/implement` 時，下列行為一律視為跳步驟，必須立即停止並改回逐步執行：
  1. **跳過前置**：略過仍未完成或仍被 `Dependencies`／phase 阻塞的 task，直接做後面的 task。
  2. **合併序列步驟**：把多個未標 `[P]`、也沒有 `Parallel Hint` 的已解鎖 task 併成同一輪實作或同一批回寫。
  3. **Phase 3 寫產品碼**：在 ALIGN / REMOVE / RED / review 寫入產品行為。
  4. **review 沒過就 Green**：Phase 3 review 仍有 issues，或尚未回寫，就開始 Feature Green。
  5. **跨 BDD 步驟**：把 `[BDD-GREEN]` 與 `[BDD-REFACTOR]` 混在同一輪完成；或讓 `/bdd` 在當前 task 以外繼續吞掉其他 step / 後續 Feature phase。
  6. **預做後續交付**：執行當前任務集時，順手寫入後續 task 才該交付的測試、實作、重構或整合內容。
  7. **未完成閘門就續跑**：當前任務集尚未完成對應驗證，或尚未回寫 `[X]`，就開始下一個任務集。
  8. **提前／批次打勾**：尚未驗證完成就改 `[X]`，或一次把多個尚未各自驗證完成的 task 一起打勾。
  9. **越界吞責任**：在 Setup／Foundational／單一 Feature task 中，偷做後續故事功能或其他 task 的完成條件。
- 若為了「比較快」而觸發以上任一項，仍屬違規。使用者寫了 `don't stop until deliver` 或 One-Shot，仍屬違規。

## Good Example

- 這個例子是好的，因為 Phase 3 停在測試層與 review。

```md
T008–T014 寫完 stepdef，T015 review 通過。
agent 回寫後才重算 T016 [BDD-GREEN]，不在 Phase 3 寫送訊 API。
```

## Bad Example

- 這個例子是壞的，因為它用效率理由把測試層與 Green 壓在同一輪。

```md
反正 RED 很簡單，順便把 Green 實作一起做完。
```

# Rule 3 - Feature 的 `[BDD-GREEN]` / `[BDD-REFACTOR]` 必須單步委派 `/bdd`

- Level: `MUST`
- 若當前 task title 含 `[BDD-GREEN]` 或 `[BDD-REFACTOR]`，本輪只能委派 `/bdd` 執行對應那一個 `requested step`，並把該 phase 的 `Test Scope` 當範疇。
- 禁止讓 `/bdd` 在同一輪內連續執行 Green 與 Refactor，或推進其他 Feature phase。
- `[BDD-GREEN]` 只做讓 `Test Scope` 轉綠的最小實作。
- `[BDD-REFACTOR]` 只在綠燈下做 behavior-preserving cleanup。
- Phase 3 的 `[BDD-ALIGN]`、`[BDD-REMOVE]`、`[BDD-RED]` 不走本規則，不委派 `/bdd`。

## Good Example

- 這個例子是好的，因為 `/bdd` 被鎖在當前 Green 與 `Test Scope`。

```md
當前 task：`T016 [BDD-GREEN]`
委派 `/bdd`：requested step=`green`，Test Scope=`單人等待與空白訊息拒絕.feature`。
本輪結束於綠燈與 `T016` 回寫。
```

## Bad Example

- 這個例子是壞的，因為它把一個 GREEN task 做成整輪 BDD。

```md
當前 task 是 `[BDD-GREEN]`。
agent 讓 `/bdd` 順手把 Phase 3 的 RED 與後續 REFACTOR 一次跑完。
```

# Rule 4 - 當前任務集邊界外的交付物一律不得預做

- Level: `MUST`
- 本輪只允許修改與驗證「當前任務集」完成條件所必需的檔案與內容。
- 不得因為共用模組方便，就提前實作後續 task 才需要的行為、測試案例、抽象層或整合接線。
- Setup task 只做本輪新增技術的套件、配置、技術環境與 smoke-test，不得寫 DSL 語意或產品行為。
- Foundational task 只建立後續實作程式、測試共用元件、入口、fixture、helper 與落點骨架，且停在該則「只做／不做」；不得偷做某個 Feature 的完整功能，也不得寫 Phase 3 的 ALIGN / REMOVE / RED 語意。

## Good Example

- 這個例子是好的，因為共用骨架停在當前 task 邊界內。

```md
當前 task：`T004` 建立聊天測試共用 helper 入口與骨架。
agent 只確認落點與函式殼，不寫各句 stepdef，也不寫送訊 API。
```

## Bad Example

- 這個例子是壞的，因為借 Foundational 之名預做後續功能。

```md
做 `T004` 時，順便把空白拒絕 API 與 Phase 3 全部 stepdef 做完。
```

# Rule 5 - 必須先驗證並回寫，才可重算下一個任務集

- Level: `MUST`
- 單一 task（或 `Parallel Hint` 批次中的每一個 task）都必須先完成對應驗證，再回寫該 task 的 `[X]`。
- 只有在當前任務集的回寫完成後，才可返回選任務流程。
- 合法平行批次仍須各自驗證後再各自回寫；不得只驗證其中一個就整批打勾。

## Good Example

- 這個例子是好的，因為 One-Shot 閘門完整。

```md
1. T008–T014 各自完成測試層
2. T015 review 通過
3. 回寫 T008–T015
4. 重新讀取 `tasks.md`，才開始 T016
```

## Bad Example

- 這個例子是壞的，因為邊寫 Green 邊說 Phase 3 大概沒問題。

```md
agent 邊寫 `T016` 邊說 `T015` 之後再補 review。
```
