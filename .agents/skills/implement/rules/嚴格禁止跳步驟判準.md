# Rule 1 - 預設一輪只推進恰好一個已解鎖 task

- Level: `MUST`
- 每一輪執行的任務集預設必須恰好包含 1 個已解鎖且未完成的 task。
- 只有當多個 task 都明示 `[P]`、彼此無前後依賴、前置條件一致，且通過 `平行執行與檔案衝突判準` 時，才可把任務集擴大為同輪平行批次。
- 未標 `[P]` 的序列 task，即使都已解鎖，也不得併成同一輪實作。
- 「續跑」只代表完成當前 task 的驗證與回寫後，再重算下一個 task；不代表本輪可一次吞掉多個序列步驟。

## Good Example

- 這個例子是好的，因為本輪只鎖定單一 task，即使後面任務已解鎖也不併入。

```md
目前已解鎖：`T006 [BDD-RED]`、之後還有 `T007 [BDD-GREEN]`。
本輪任務集 = {T006}。
完成驗證並回寫 `[X]` 後，才重算並進入 `T007`。
```

## Bad Example

- 這個例子是壞的，因為把未標 `[P]` 的序列 task 一次打包，等於跳過逐步閘門。

```md
`T006`、`T007`、`T008` 都看得到。
agent 決定本輪一次做完 RED、GREEN、REFACTOR，最後再一起打勾。
```

# Rule 2 - 下列行為一律視為跳步驟，嚴格禁止

- Level: `MUST`
- 執行 `/implement` 時，下列行為一律視為跳步驟，必須立即停止並改回逐步執行：
  1. **跳過前置**：略過仍未完成或仍被 `Dependencies`／phase 阻塞的 task，直接做後面的 task。
  2. **合併序列步驟**：把多個未標 `[P]` 的已解鎖 task 併成同一輪實作或同一批回寫。
  3. **跨 BDD 步驟**：把 `[BDD-RED]`、`[BDD-GREEN]`、`[BDD-REFACTOR]` 混在同一輪完成；或讓 `/bdd` 在當前 task 以外繼續吞掉其他 step / 後續 task。
  4. **預做後續交付**：執行當前 task 時，順手寫入後續 task 才該交付的測試、實作、重構、UI 或整合內容。
  5. **未完成閘門就續跑**：當前 task 尚未完成對應驗證，或尚未回寫 `[X]`，就開始修改下一個 task 的檔案或載入下一個 task 的參照作為執行依據。
  6. **提前／批次打勾**：尚未驗證完成就改 `[X]`，或一次把多個尚未各自驗證完成的 task 一起打勾。
  7. **越界吞責任**：在 Setup／Foundational／單一 feature file task 中，偷做後續故事功能、整合責任或其他 task 的完成條件。
- 若為了「比較快」「上下文已熟悉」「後面反正也要做」而觸發以上任一項，仍屬違規，不得合理化。

## Good Example

- 這個例子是好的，因為它把禁止清單當成硬閘門，遇到誘惑時退回單步。

```md
做 `T006 [BDD-RED]` 時，測試紅燈已正確。
agent 停在紅燈，回寫 `T006`，不開始寫 production code，也不預開 `T007`。
```

## Bad Example

- 這個例子是壞的，因為它用效率理由合理化多種跳步。

```md
反正 RED 很簡單，順便把 GREEN 實作與 REFACTOR 整理一起做完，比較省 token。
同時先把下一個 feature file phase 的測試骨架也鋪好。
```

# Rule 3 - `[BDD-*]` task 必須單步委派，禁止跨步與越界續推

- Level: `MUST`
- 若當前 task title 含 `[BDD-RED]`、`[BDD-GREEN]` 或 `[BDD-REFACTOR]`，本輪只能委派 `/bdd` 執行對應那一個 `requested step`。
- 委派時必須明示：當前 `feature file` phase、單一 `requested step`、同模組 DSL、實際使用的介面根共用 DSL rows，以及本輪不得跨步。
- 禁止讓 `/bdd` 在同一輪內連續執行超過一個 BDD 步驟，或在當前 task 以外繼續推進其他 feature file phase。
- `[BDD-RED]` 完成條件停在正確紅燈；不得為了「看起來比較完整」而繼續寫 production code。
- `[BDD-GREEN]` 只做讓當前紅燈轉綠的最小實作；不得偷做後續 feature file phase 或提前重構到改變行為。
- `[BDD-REFACTOR]` 只在綠燈下做 behavior-preserving cleanup；不得夾帶新行為。

## Good Example

- 這個例子是好的，因為 `/bdd` 被嚴格鎖在當前 task 授權的單一 step。

```md
當前 task：`T012 [BDD-GREEN]`
委派 `/bdd`：requested step=`green`，scope=`features/backend/三連猜/三連猜猜中與對局結束.feature`。
本輪結束於綠燈與 `T012` 回寫，不進入 REFACTOR，也不推下一個 feature file phase。
```

## Bad Example

- 這個例子是壞的，因為它把一個 GREEN task 做成整輪 BDD。

```md
當前 task 是 `[BDD-GREEN]`。
agent 呼叫 `/bdd` 時不鎖 single step，讓它順手把前面的 RED、當前 GREEN、後續 REFACTOR 一次跑完。
```

# Rule 4 - 當前 task 邊界外的交付物一律不得預做

- Level: `MUST`
- 本輪只允許修改與驗證「當前任務集」完成條件所必需的檔案與內容。
- 不得因為共用模組方便，就提前實作後續 task 才需要的行為、測試案例、抽象層或整合接線。
- 若實作當前 task 時發現後續 task 會受影響，最多只能留下最小必要的暫時邊界或 TODO 說明；不得直接把後續 task 做完並提前打勾。
- Setup／Foundational task 只能建立入口、fixture、helper 或共同依賴骨架，不得偷做某個故事 feature file 的完整功能。

## Good Example

- 這個例子是好的，因為共用骨架停在當前 task 邊界內。

```md
當前 task：`T003` 建立技能欄位 schema 骨架。
agent 只加欄位／model 增量，不實作 change-answer 或 triple-guess 行為。
```

## Bad Example

- 這個例子是壞的，因為借 Foundational 之名預做後續故事功能。

```md
做 `T003` schema 骨架時，順便把 change-answer API、規則與前端按鈕全部做完。
理由是「後面一定用得到」。
```

# Rule 5 - 必須先驗證並回寫，才可重算下一個 task

- Level: `MUST`
- 單一 task（或合法 `[P]` 批次中的每一個 task）都必須先完成對應驗證，再回寫該 task 的 `[X]`。
- 只有在當前任務集的回寫完成後，才可返回選任務流程，重新計算下一個已解鎖 task。
- 回寫完成前，禁止開始下一個 task 的實作、禁止把下一個 task 的參照當成當前執行依據、禁止預改其交付檔案。
- 合法平行批次仍須各自驗證後再各自回寫；不得只驗證其中一個就整批打勾。

## Good Example

- 這個例子是好的，因為續跑閘門完整且不可壓縮。

```md
1. 完成 `T006` 實作
2. 跑對應驗證，確認紅燈正確
3. 回寫 `T006` 為 `[X]`
4. 重新讀取 `tasks.md`，才開始 `T007`
```

## Bad Example

- 這個例子是壞的，因為把驗證／回寫與下一步實作壓縮成同一動作。

```md
agent 邊寫 `T007` 邊說 `T006` 大概沒問題，之後再補測試與打勾。
```
