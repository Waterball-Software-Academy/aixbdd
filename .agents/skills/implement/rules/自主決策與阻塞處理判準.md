# Rule 1 - 實作期間不得因一般規格缺口而停下來向使用者要澄清

- Level: `MUST`
- 若缺口仍可透過當前 task、phase 的 `Shared Must Read`、phase 的 `Boundary`、`Dependencies`、既有程式碼或技術棧邊界收斂，必須自行做出專業判斷，不得先停下來問使用者。
- 若當前 task 位於 `Setup` / `Foundational` 或其他一般 phase，則改以該 task 的 `Read`、`Dependencies`、既有程式碼與最小可逆方案作為決策依據。
- 只有在工具、權限、檔案缺失或環境限制讓後續步驟客觀不可執行時，才可停止續跑。

## Good Example

- 這個例子是好的，因為它先用已知約束自行收斂，而不是把一般模糊點立刻升級成使用者問題。

```md
`FR-017` 尚未明定先手規則。
agent 先讀當前 phase 的 `Boundary`，確認假設必須被侷限在單一 domain helper，
於是採最小可替換的預設實作，並把風險留在該邊界內。
```

## Bad Example

- 這個例子是壞的，因為它在已有足夠約束可收斂的情況下，仍停下來等使用者回答。

```md
agent 看到先手規則未明定，就立刻回報「請問是房主先手還是隨機？」並中止整個實作流程。
```

# Rule 2 - 當模糊處無法完全消失時，必須選擇最小變更、最低耦合且可隔離的方案

- Level: `MUST`
- 若多個方案都能滿足目前資訊，應優先選擇最小變更、最低耦合、最易驗證且最可逆的方案。
- 若當前 phase 的 `Boundary` 已指定不確定性應集中在哪些檔案、模組或責任邊界，必須把假設侷限在那些邊界，不得擴散到其他任務面。
- 不得為了短期方便，把仍未收斂的規則硬編碼到多個 handler、page 或 state module。

## Good Example

- 這個例子是好的，因為它把模糊點壓縮在可替換的單一邊界內。

```md
agent 需要先決定 `currentTurnPlayerId` 的預設來源。
它把決策集中在 `game.js` 的單一 helper，而不是把相同判斷散落到 socket handler、presenter 與前端 state。
```

## Bad Example

- 這個例子是壞的，因為它把未澄清規則複製到多個層面，讓之後修規則時需要到處回收。

```md
agent 同時在 `gameHandler.js`、`roomStore.js`、`main.js` 內各自寫了一套先手判斷，三處邏輯還不完全一致。
```

# Rule 3 - 無法完美前進時，仍應採最佳可行替代並揭露殘餘風險

- Level: `SHOULD`
- 若理想路徑受限於環境、工具或外部資源，但仍存在可行替代路徑，應先採替代方案繼續推進，而不是過早整體停工。
- 完成回報時應清楚揭露採用的替代方案、受限原因與仍待外部條件解除的部分。

## Good Example

- 這個例子是好的，因為它先完成可完成部分，並把真正受限點說清楚。

```md
agent 無法跑完整的整合驗證，但仍先完成 targeted tests、lint 與手動驗證腳本更新，
最後在回報中標註整合驗證受限於本機環境。
```

## Bad Example

- 這個例子是壞的，因為它把局部受限誤判成整體無法前進。

```md
agent 發現其中一個驗證工具暫時不可用，就直接停止所有後續 task，沒有先完成其他仍可獨立完成的部分。
```
