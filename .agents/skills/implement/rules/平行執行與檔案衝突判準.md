# Rule 1 - `[P]` 是唯一可同輪例外，且只代表可平行、不代表必須平行

- Level: `MUST`
- 在 `/implement` 預設單 task 前進的前提下，任務帶有 `[P]` 時，只表示它在理論上可與其他 `[P]` task 平行，不表示 agent 必須把它們綁成同一輪。
- 只有在任務彼此都明示 `[P]`、沒有前後依賴、前置條件一致，且實際修改檔案與驗證面互不衝突時，才可平行推進。
- 未標 `[P]` 的序列 task 不得藉由本規則併批；若平行與序列兩種做法都成立，允許選擇較穩定、較容易驗證的序列做法。

## Good Example

- 這個例子是好的，因為它把 `[P]` 視為許可而不是命令，仍先檢查實際衝突面。

```md
`T002 [P]` 與 `T003 [P]` 都已解鎖。
agent 先檢查兩者是否共享 `package.json`、環境變數檔或同一個驗證腳本；若沒有，再決定是否平行。
```

## Bad Example

- 這個例子是壞的，因為它看到 `[P]` 就直接平行，沒有先判斷實際修改與驗證衝突。

```md
兩個 task 都標了 `[P]`。
agent 直接同時修改 `frontend/package.json` 與 `frontend/vite.config.js`，卻沒有注意兩者其實共用同一套啟動驗證流程。
```

# Rule 2 - 共享檔案、共享模組邊界或共享驗證面時，必須改成序列執行

- Level: `MUST`
- 若兩個 task 會修改同一檔案、同一模組責任邊界，或需要依賴同一份尚未穩定的驗證結果，必須改成序列執行。
- 即使任務分屬不同端點區塊，只要共享 `main.js`、`appStore.js`、`roomStore.js`、`package.json` 等匯聚檔，也應視為衝突面。
- 當存在明確的整合 task 時，前置 task 完成後應由整合 task 收斂，不應讓多個前置 task 各自偷偷完成整合。

## Good Example

- 這個例子是好的，因為它把共享匯聚檔視為衝突面，並讓整合 task 最後收斂。

```md
`T011` 修改 `pairingEntry.js`，`T012` 修改 `main.js` 與 `appStore.js`。
即使 `T011` 可單獨進行，agent 仍把 `T012` 保留為最後的整合收斂點，而不是讓 `T011` 順手把所有 socket flow 都接完。
```

## Bad Example

- 這個例子是壞的，因為它讓前置 task 越界吞掉整合責任，破壞 `tasks.md` 的切分邊界。

```md
agent 在做 UI task 時順手改了 `main.js`、`appStore.js` 與 socket client，把原本屬於跨端整合 task 的內容一起做完。
```

# Rule 3 - 平行批次完成後，應先各自驗證，再做整體收斂驗證

- Level: `SHOULD`
- 若本輪確實存在平行批次，應先確認每個 task 自己的局部完成條件，再做一次整體收斂驗證。
- 不應只驗證其中一個 task 就把整批視為完成。

## Good Example

- 這個例子是好的，因為它先看局部，再看整體。

```md
兩個 `[P]` 任務分別完成後，agent 先各自檢查啟動與語法，再補一次整體流程驗證，確認批次沒有互相破壞。
```

## Bad Example

- 這個例子是壞的，因為它把批次內其中一項驗證成功，錯誤當成整批都完成。

```md
agent 只跑了 frontend 的檢查，就把同輪 backend 與 frontend 的兩個 task 一起改成 `[X]`。
```
