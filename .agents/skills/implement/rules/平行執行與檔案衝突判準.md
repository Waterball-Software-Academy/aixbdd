# Rule 1 - `[P]` 是可平行許可；Parallel Hint 則是必須一次派出的批次

- Level: `MUST`
- 在 `/implement` One-Shot 一輪恰好 1 個 task 的前提下，任務帶有 `[P]` 且沒有 `Parallel Hint` 時，只表示它在理論上可與其他 `[P]` task 平行，不表示必須綁成同一輪。
- 若當前 phase 有 `Parallel Hint`，必須依 `rules/ParallelHint平行Subagent與衝突Merge判準.md` 一次派出 Hint 列出的 `[P]` 批次。
- 未標 `[P]` 的序列 task 不得併批。Feature phase 預設序列。

## Good Example

- 這個例子是好的，因為 Feature Green 仍序列，Phase 3 則遵守 Hint。

```md
Phase 3 有 Parallel Hint：一次派出 T008–T014。
Phase 4A 的 T016 [BDD-GREEN] 與 T017 [BDD-REFACTOR] 未標 [P]，仍序列。
```

## Bad Example

- 這個例子是壞的，因為它看到 `[P]` 就無視 Hint 範圍，或把 Feature Green 也平行掉。

```md
把 T016 [BDD-GREEN] 與 T018 [BDD-GREEN] 一次平行改同一份 store。
```

# Rule 2 - Feature phase 共享檔案時必須序列；Phase 3 同檔由後寫 subagent merge

- Level: `MUST`
- Feature phase 或非 Phase 3 的 task 若會修改同一檔案、同一模組責任邊界，或需要依賴同一份尚未穩定的驗證結果，必須序列執行。
- Phase 3 的 `[P]` 批次即使寫同一檔，仍各派 subagent；後寫入者先讀最新檔再 merge。細節以 `ParallelHint平行Subagent與衝突Merge判準.md` 為準。
- 當存在明確的整合 task 時，前置 task 完成後應由整合 task 收斂。

## Good Example

- 這個例子是好的，因為它把兩種衝突策略分開。

```md
Phase 3：T008 與 T009 都寫 `操作與斷言.py`，仍平行；後寫者 merge。
Phase 4：T016 與 T018 都改 `store.py`，改成序列。
```

## Bad Example

- 這個例子是壞的，因為它用舊的「同檔必序列」擋住 Phase 3。

```md
Parallel Hint 要 T008–T011 平行，但因同檔改成一個一個做。
```

# Rule 3 - 平行批次完成後，應先各自驗證，再做整體收斂驗證

- Level: `SHOULD`
- 若本輪確實存在平行批次，應先確認每個 task 自己的局部完成條件，再做一次整體收斂驗證。
- 不應只驗證其中一個 task 就把整批視為完成。
- Phase 3 的整體收斂驗證由 review task 承擔。

## Good Example

- 這個例子是好的，因為它先看局部，再看 review。

```md
T008–T014 各自回報對齊結果後，T015 review 跑本輪所有 Test Scope，確認沒有 undefined step。
```

## Bad Example

- 這個例子是壞的，因為它只驗證其中一項就整批打勾。

```md
agent 只看了 T008 的 diff，就把 T008–T014 一起改成 `[X]`。
```
