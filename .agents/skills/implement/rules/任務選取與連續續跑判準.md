# Rule 1 - 未指定範圍時，從上到下找第一個已解鎖 task 當 One-Shot 起點

- Level: `MUST`
- 若使用者明確指定 `T###`、`US#`、phase 或其他範圍，必須先在指定範圍內選 task。
- 若使用者未指定範圍，必須依 `tasks.md` 由上到下找到第一個「未完成且已解鎖」的 task 作為 One-Shot 起點。
- `已解鎖` 必須依 `Dependencies`、phase / story 前置關係與目前勾選狀態判斷，不得自行跳過仍被阻塞的 task。

## Good Example

- 這個例子是好的，因為未指定範圍時仍依 `tasks.md` 順序從第一個已解鎖 task 開始。

```md
使用者只說「請實作」。
agent 先讀 `tasks.md`，發現 `T001`、`T002` 都未完成，但 `T001` 是第一個已解鎖 task。
agent 先從 `T001` 開始，而不是直接跳去後面的 `US2` 任務。
```

## Bad Example

- 這個例子是壞的，因為它跳過前面仍未完成或未解鎖的任務。

```md
使用者只說「請實作」。
agent 直接挑 `T018`，理由是它看起來比較有趣，沒有先檢查前面的 `Setup` 與 `Foundational` 是否完成。
```

# Rule 2 - by default 就是 don't stop until deliver / One-Shot

- Level: `MUST`
- 預設不是做完單一 task 就停止。驗證並回寫 `[X]` 後，必須重算下一個已解鎖且屬於本次範圍的 task，直到交付。
- 使用者不必再寫 `don't stop until deliver` 或 One-Shot。寫了也不改變一輪任務集的邊界。
- One-Shot 不是把後面的序列 task 一次攤開，也不是跳過驗證與回寫。
- 只有在指定範圍已完成、已無技術上可行的下一步，或外部限制讓後續步驟客觀不可執行時，才可停止。
- 重新計算時必須以最新的 `tasks.md` 勾選狀態與實際程式碼狀態為準。

## Good Example

- 這個例子是好的，因為完成 `T001` 後立刻勾選並重算下一筆。

```md
agent 完成並驗證 `T001`，回寫 `[X]`。
接著重新讀取 `tasks.md`，判斷 `T002` 已解鎖，再收斂下一輪任務集。
```

## Bad Example

- 這個例子是壞的，因為它把 One-Shot 做成一次攤開，或做成做 1 個就停。

```md
agent 完成 `T001` 之後直接回報「本次已完成下一個 task」，沒有重算。
或把 T005–T230 一次派給兩個 subagent，最後再一起打勾。
```

# Rule 3 - One-Shot 的一輪任務集恰好 1 個；有 Parallel Hint 則收整批 `[P]`

- Level: `MUST`
- One-Shot 的每一輪必須只選恰好 1 個已解鎖 task 作為本輪任務集，不得一次攤開同 phase 或多個序列步驟。
- 若當前 phase 有 `Parallel Hint`，本輪任務集必須是 Hint 列出的 `[P]` 批次，不是只拿第一個已解鎖 task。
- 沒有 `Parallel Hint` 時，只有在多個 task 都明示 `[P]`、前置條件一致，且 `平行執行與檔案衝突判準` 允許時，才可擴大為同輪平行批次。
- 未標 `[P]` 的 task 即使都已解鎖，也必須序列執行。
- 跳步驟的細部禁止事項，以 `嚴格禁止跳步驟判準` 為準。

## Good Example

- 這個例子是好的，因為有 Hint 就收整批，Feature 仍單 task。

```md
Phase 3 Parallel Hint 列出 T008–T014。
本輪任務集 = {T008–T014}，不是只做 T008。
T016 [BDD-GREEN] 未標 [P]，下一輪只做 T016。
```

## Bad Example

- 這個例子是壞的，因為它忽略 Hint，或把整個 Setup 一次打包。

```md
agent 看到 Phase 3 有 7 個 [P]，仍只做 T008。
或看到 Phase 1 Setup 還有 3 個未標 [P] 的 task，一次全做完。
```
