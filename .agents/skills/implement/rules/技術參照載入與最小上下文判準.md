# Rule 1 - 實作前必須先讀 phase 共享參照或當前 task 的 `Read`

- Level: `MUST`
- 若當前 task 位於 `Feature File` phase 或 `NFR 重構` phase，開始實作前必須先讀取該 phase 的 `Shared Must Read` 指定文件與具體部位。
- 若當前 task 位於 `Setup`、`Foundational` 或其他一般 phase，開始實作前必須先讀取該 task 的 `Read` 指定文件與具體部位。
- 參照要求是精確載入，不得只讀同檔其他位置就視為已滿足。
- 若同一輪包含多個合法 `[P]` task，必須分別確認每個 task 的必要參照都已覆蓋。

## Good Example

- 這個例子是好的，因為它先讀 phase 或 task 明示的必要參照，再開始寫碼。

```md
agent 要做 `T012 [BDD-GREEN]`。
它先讀當前 feature file phase 的 `Shared Must Read`，確認三連猜結束語意；
接著才在需要時補讀 `contracts/openapi.yaml` 與 `data-model.dbml`。
```

## Bad Example

- 這個例子是壞的，因為它只看 task 標題，沒有讀取真正授權的參照面。

```md
agent 要做 `T012 [BDD-GREEN]`。
它沒有讀 `Shared Must Read`，只因為知道這是三連猜結束流程，就直接開始改 handler。
```

# Rule 2 - `Extra Read` 與其他 artifacts 只在需要時才補讀

- Level: `MUST`
- `Extra Read` 只在當前 task 真的列出額外文件，或需要補足共享檔案約束、視覺細節、驗證方式、整合決策時才讀。
- 不得把 `tasks.md`、`plan.md`、`research.md`、`contracts/`、`data/`、`ui/` 全部預先全文載入後再開始動作。
- 若已能依 `Shared Must Read` 或當前 task 的 `Read` 與現有程式碼收斂方案，就不應額外擴張上下文。

## Good Example

- 這個例子是好的，因為它先靠必要參照完成主要判斷，只在需要時才補 `Extra Read`。

```md
agent 要做 `T009 [BDD-GREEN]`。
它先讀該 phase 的 `Shared Must Read`；
只有在要對齊畫面與資料模型時，才補讀 `ui/ui-plan.md` 與 backend feature file。
```

## Bad Example

- 這個例子是壞的，因為它把所有 artifacts 一次載入，造成上下文膨脹卻沒有提升當前 task 的決策品質。

```md
agent 準備做 `T021`。
它先把 `spec.md`、`plan.md`、`research.md`、`techstack.md`、`contracts/openapi.yaml`、`data-model.dbml`、所有 `ui/*.html` 全讀一遍，之後才開始判斷畫面錯誤回饋。
```

# Rule 3 - 只有在共享修改面或整合風險存在時才補讀相鄰 task

- Level: `SHOULD`
- 若當前 task 會修改與前後 task 共用的檔案、共用狀態模型或共用驗證面，應補讀相鄰 task 的描述與參照，避免局部正確、整體失配。
- 若當前 task 是獨立且邊界清楚的單點任務，則不必為了形式完整而額外補讀相鄰 task。

## Good Example

- 這個例子是好的，因為它只在真的共享修改面時才往前後 task 延伸閱讀。

```md
agent 要做 `frontend/src/main.js` 的跨端整合 task。
由於同檔前後 task 都會動到同一段狀態同步邏輯，
agent 補讀相鄰 task，確認 page flow 與 app state 不會互相覆寫。
```

## Bad Example

- 這個例子是壞的，因為它把「補讀相鄰 task」誤變成每次都要整段通讀整個故事。

```md
agent 要做一個只改 `backend/.env.example` 的 setup task。
它仍然把整個 `US3` 區塊全部補讀一遍，卻沒有任何共享檔案或整合需求。
```

# Rule 4 - MODIFY / DELETE 必須載入既有自動化測試落點

- Level: `MUST`
- 當前 task 若對應 truth-delta 的 `MODIFY` 或 `DELETE`，除了 `Shared Must Read` 與 `Extra Read` 外，還必須載入或定位受影響的既有 feature scenarios、step definitions、fixtures、helpers、focused tests 與產品分支。
- 若 `tasks.md` 已明列既有測試落點，必須讀取指定檔案；若未明列，必須先做最小範圍查找並回報 `tasks.md` 缺口。
- 不得只讀最新版 truth feature/dsl 就開始實作，因為舊測試可能仍在保護過期 truth。

## Good Example

- 這個例子是好的，因為修改 DSL 時同步讀取既有 step definition。

```md
Shared Must Read:
- `specs/truth/features/backend/房間聊天/dsl.md`
- `backend/features/steps/modules/房間聊天/操作與斷言.py`
```

## Bad Example

- 這個例子是壞的，因為沒有讀既有測試落點。

```md
只讀 `specs/truth/features/backend/房間聊天/dsl.md` 後就直接修改產品碼。
```
