# Rule 1 - `ui/ui-plan.md` 是控制平面，`ui/*.html` 是可 review 的產品雛形

- Level: `MUST`
- `ui-plan` 的產出順序必須是先定稿 `ui/ui-plan.md`，再依這份 plan 產出 `ui/*.html`。
- `ui/ui-plan.md` 的責任是整理介面範圍、視覺方向、畫面與流程、驗證與靜態雛形輸出規劃。
- `ui/*.html` 的責任是把上述 plan 落地成可點擊、可換頁、可感受產品節奏的高保真靜態雛形。
- 不可把兩者混成一份產物，也不可讓 HTML 先成形後再倒推關鍵流程決策。

## Good Example

- 這個例子是好的，因為它先用 `ui-plan.md` 收斂畫面與 flow，再用多個 HTML 真正呈現產品。

```md
1. 先完成 `ui/ui-plan.md`
   - 定義 `ui/index.html`、`ui/product-detail.html`、`ui/checkout.html`
   - 定義每頁的主要目的與換頁關係

2. 再依 plan 產出 HTML
   - `ui/index.html`
   - `ui/product-detail.html`
   - `ui/checkout.html`
```

## Bad Example

- 這個例子是壞的，因為它先畫 HTML，再回頭補 plan，導致單一溯源不成立。

```md
1. 先隨手做出三個 HTML
2. 後面再看要不要補 `ui/ui-plan.md`
3. 發現流程衝突時，再回頭改所有檔案
```

# Rule 2 - HTML 雛形必須看起來像產品，不是說明文件

- Level: `MUST`
- `ui/*.html` 中只能放產品真的會顯示給使用者的內容，例如標題、欄位、狀態、CTA、錯誤訊息、結果摘要與假資料。
- 不可把分析備註、元件樹、實作 TODO、欄位解說或 review 說明直接寫進 HTML 畫面。
- 若某段資訊是給開發者或 reviewer 看的，應留在 `ui/ui-plan.md`，而不是放進產品畫面。

## Good Example

- 這個例子是好的，因為 HTML 畫面只呈現使用者真的會看到的產品內容。

```html
<h1>確認購物車後立即結帳</h1>
<p>查看商品、折扣與配送資訊後送出本次訂單</p>
<input placeholder="輸入折扣碼" />
<button>套用優惠</button>
```

## Bad Example

- 這個例子是壞的，因為它把說明文件內容直接塞進產品畫面。

```html
<h1>畫面一：購物車與結帳畫面</h1>
<p>這一頁的主要目的是讓使用者確認訂單，後續會導到成功頁。</p>
<p>TODO: 之後這裡可能要改成真正的產品 UI。</p>
```
