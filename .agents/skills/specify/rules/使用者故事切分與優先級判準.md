# Rule 1 - 使用者故事必須以可獨立驗證的使用者價值切分

- Level: `MUST`
- 每個使用者故事都必須代表一段可被單獨理解、單獨驗證、單獨展示的使用者價值，而不是單純把功能清單或技術工作拆成幾段。
- 若某段需求只有內部實作步驟、資料處理細節或 UI 元件名稱，卻沒有對應清楚的使用者成果，不應直接拿來當使用者故事標題。
- 切分後的故事應能回答「作為誰、想完成什麼、因此得到什麼價值」。

## Good Example

- 這個例子是好的，因為三個故事都對應獨立的使用者成果，而不是把需求照句子順序硬拆。

````md
### 使用者故事 1 - 依日期自動整理照片 (Priority: P1)

作為想快速整理生活照片的使用者，我希望在匯入照片後，系統能自動依日期將照片分配到不同相簿，讓我不必手動建立與分類每一批照片。

### 使用者故事 2 - 在首頁瀏覽日期相簿 (Priority: P2)

作為想快速瀏覽整理結果的使用者，我希望在首頁一次看到所有日期相簿，方便我快速判斷內容與選擇要整理的相簿。
````

## Bad Example

- 這個例子是壞的，因為它把功能句子或實作片段直接當故事，沒有形成完整的使用者價值切片。

````md
### 使用者故事 1 - 匯入照片
### 使用者故事 2 - 日期欄位解析
### 使用者故事 3 - 拖放元件
````

# Rule 2 - 使用者故事應依商業價值與交付順序排列優先級

- Level: `MUST`
- 使用者故事的 Priority 必須反映使用者價值與交付順序，讓 P1 代表最先需要被證明的核心價值。
- 若後續故事的價值建立在前一故事已成立的結果上，優先級應往後排，不可只依 prompt 出現順序決定。
- 每個故事都應補上 `為何為此優先級`，說清楚排序理由，而不是只標 P1 / P2 / P3。

## Good Example

- 這個例子是好的，因為它先交付核心整理能力，再交付瀏覽與排序等後續價值。

````md
### 使用者故事 1 - 依日期自動整理照片 (Priority: P1)
**為何為此優先級**: 這是整個產品的核心價值；若無法自動完成日期分組，後續的瀏覽與排序流程都無法成立。

### 使用者故事 2 - 在首頁瀏覽日期相簿 (Priority: P2)
**為何為此優先級**: 使用者完成自動整理後，下一個高價值行為就是檢視結果。
````

## Bad Example

- 這個例子是壞的，因為它只按敘述順序或個人偏好標優先級，沒有對齊交付依賴與商業價值。

````md
### 使用者故事 1 - 拖放調整照片順序 (Priority: P1)
**為何為此優先級**: 因為拖放看起來最酷。

### 使用者故事 2 - 依日期自動整理照片 (Priority: P2)
**為何為此優先級**: 自動分組可以之後再補。
````

# Rule 3 - 每個使用者故事都應保留最小必要的驗證資訊

- Level: `SHOULD`
- 每個使用者故事應至少具備故事敘述、優先級原因、獨立驗證方式與 1 個以上驗收情境，避免只剩標題與需求清單。
- `獨立驗證方式` 應描述如何在只實作該故事時，仍能驗證其是否成立。
- 驗收情境應優先覆蓋故事成立的主要成功路徑，再視需要補入高風險例外情境。

## Good Example

- 這個例子是好的，因為它補足了最小必要的驗證資訊，讓故事不只是需求容器。

````md
### 使用者故事 1 - 依日期自動整理照片 (Priority: P1)

作為想快速整理生活照片的使用者，我希望在匯入照片後，系統能自動依日期將照片分配到不同相簿。

**獨立驗證方式**: 匯入一組包含多個日期的照片，確認系統建立對應相簿並將照片放入正確分組。

**驗收情境**:
1. **Given** 使用者匯入多張分別來自不同日期的照片，**When** 匯入完成，**Then** 系統會建立對應日期相簿並正確分配照片。
````

## Bad Example

- 這個例子是壞的，因為它只有故事標題，缺少如何驗證故事成立的資訊。

````md
### 使用者故事 1 - 依日期自動整理照片 (Priority: P1)

照片要能自動整理。
````
