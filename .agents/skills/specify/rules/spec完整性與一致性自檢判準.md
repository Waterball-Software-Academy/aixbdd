# Rule 1 - 每個使用者故事都必須形成完整的最小驗證切片

- Level: `MUST`
- 每個使用者故事都必須至少包含故事敘述、Priority、優先級原因、獨立驗證方式與 1 個以上驗收情境，讓讀者能理解這個故事如何被單獨驗證。
- 每個故事都應有專屬的 `功能需求（FR）` 區塊；`非功能需求（NFR）` 若確實沒有，可省略或刪除，但不可留下空殼小節。
- 若某個故事缺少必要驗證資訊，只剩標題與需求條列，應視為故事尚未完成，而不是格式已合格。

## Good Example

- 這個例子是好的，因為它保留了故事成立所需的最小驗證資訊與需求歸戶。

````md
### 使用者故事 1 - 依日期自動整理照片 (Priority: P1)

作為想快速整理生活照片的使用者，我希望在匯入照片後，系統能自動依日期將照片分配到不同相簿。

**為何為此優先級**: 這是整個產品的核心價值。

**獨立驗證方式**: 匯入一組包含多個日期的照片，確認系統建立對應相簿並將照片放入正確分組。

**驗收情境**:
1. **Given** 使用者匯入多張不同日期的照片，**When** 匯入完成，**Then** 系統會建立對應日期相簿並正確分配照片。

**功能需求（FR）**:
- **FR-001**: 系統 MUST 允許使用者匯入一張或多張照片。
````

## Bad Example

- 這個例子是壞的，因為故事缺少驗證與需求歸戶資訊，還不足以成為完整切片。

````md
### 使用者故事 1 - 依日期自動整理照片 (Priority: P1)

照片要能依日期整理。
````

# Rule 2 - 全域需求必須真的剩下「故事外但仍必要」的內容

- Level: `MUST`
- `全域需求` 區段只能保留跨故事需求或無法合理歸屬單一故事的條目；若全域需求為空，可刪除該小節中的空白內容，但應保留需求區段的整體結構意圖。
- 自檢時應回頭確認是否仍有故事專屬需求被誤留在全域需求，或全域需求中的條目其實已能合理歸戶到某個故事。
- 不可讓全域需求重新變成舊式的 FR / NFR 總表。

## Good Example

- 這個例子是好的，因為全域需求只留下跨故事限制，沒有回頭變成總需求池。

````md
## 需求 *(必填)*

### 全域需求

#### 功能需求
- **FR-003**: 系統 MUST 將所有相簿維持為單一層級的頂層相簿，且不得出現相簿巢狀結構。
````

## Bad Example

- 這個例子是壞的，因為它把所有故事的需求又集中回全域區，破壞新的階層設計。

````md
## 需求 *(必填)*

### 全域需求

#### 功能需求
- **FR-001**: 系統 MUST 允許使用者匯入照片。
- **FR-005**: 系統 MUST 在首頁顯示日期相簿。
- **FR-007**: 使用者 MUST 能夠拖放重新排列照片。
````

# Rule 3 - 成功標準必須可量測，假設不可偷渡新需求

- Level: `MUST`
- `成功標準` 必須可量測、可驗證，避免只寫抽象感受或空泛願景。
- `假設` 只能記錄目前推理成立所依賴的合理前提、範圍邊界或既有條件，不可偷偷引入新的必做功能。
- 若某條內容一旦拿掉就會改變產品必備行為，它更可能是需求，而不是假設。

## Good Example

- 這個例子是好的，因為成功標準可驗證，假設則明確表達前提與邊界。

````md
### 可量測成果
- **SC-001**: 在驗收資料集中，100% 具備有效日期資訊的照片都能自動出現在對應的日期相簿中。

## 假設
- 拖放排序僅調整同一日期相簿內的顯示順序，不包含跨相簿搬移。
````

## Bad Example

- 這個例子是壞的，因為成功標準不可量測，假設也夾帶了新的產品要求。

````md
### 可量測成果
- **SC-001**: 使用者會覺得整理照片很方便。

## 假設
- 系統必須支援 AI 自動生成相簿名稱與封面。
````

# Rule 4 - 遇到低風險未定細節時，應保留缺口而不是硬補

- Level: `SHOULD`
- 若整份 spec 的主要故事、需求歸戶與驗收邏輯都已成立，但仍有少數細節未拍板，應優先用 `NEEDS CLARIFICATION` 標記或在假設中明示前提，而不是假裝需求已經被確認。
- 若缺口已影響核心流程、故事切分或正式需求邏輯，就不屬於低風險細節，應回到 `/clarify`。
- 自檢時應特別檢查文件中是否出現看似完整、實際上沒有來源依據的數值門檻、互動規則或範圍限制。

## Good Example

- 這個例子是好的，因為它保留缺口並明確揭露尚未確認之處。

````md
- **NFR-004**: 系統 MUST 在排序失敗時提供可理解的恢復指引 [NEEDS CLARIFICATION: 尚未指定是否需要一步還原或重試機制]
````

## Bad Example

- 這個例子是壞的，因為它把沒有來源的細節寫成既定需求。

````md
- **NFR-004**: 系統 MUST 在排序失敗時以三步驟精靈模式引導使用者完成恢復。
````
