# Rule 1 - 只有高影響缺口才應升級到 `/clarify`

- Level: `MUST`
- 只有當缺口會改變使用者故事切分、需求歸戶、主要流程、角色權限、範圍邊界、正式驗收標準或成功標準時，才應升級到 `/clarify`。
- 若某項未定細節只影響局部 wording、次要互動、單一數值門檻或可安全延後的體驗選項，不應直接升級到 `/clarify`。
- 不可把所有模糊處都丟給 `/clarify`，讓上游 skill 失去先行收斂需求的責任。

## Good Example

- 這個例子是好的，因為它只把會改變核心對戰規則的缺口升級為 clarify。

````md
需求：全線上 PVP 1A2B。

高影響缺口：
- 先手規則是否由房主、加入者或隨機決定
- 斷線時是暫停、判負還是等待重連

決策：
- 升級到 `/clarify`
````

## Bad Example

- 這個例子是壞的，因為它把低風險呈現細節也一併升級成 clarify。

````md
需求：全線上 PVP 1A2B。

低影響細節：
- 等待中按鈕要寫「開始」還是「開始遊戲」
- 房間卡片主色偏藍還是偏綠

決策：
- 全部升級到 `/clarify`
````

# Rule 2 - 本輪 clarify 只收斂最高影響的 1 至 3 題

- Level: `MUST`
- `specify` 在委派 `/clarify` 前，必須先自行排序缺口，只把本輪最高影響的 1 至 3 題交給 `/clarify`。
- 若高影響缺口超過 3 題，應保留最關鍵的 1 至 3 題先問，其餘留待後續輪次或在 spec 中揭露剩餘風險。
- 不可把未整理的一長串疑問原樣丟給 `/clarify`。

## Good Example

- 這個例子是好的，因為它先做排序，再交給 clarify 處理本輪最關鍵問題。

````md
本輪缺口排序：
1. 第一版範圍
2. 權限角色
3. 成功標準門檻
4. 錯誤提示文案

委派：
- 本輪只把前 3 題交給 `/clarify`
````

## Bad Example

- 這個例子是壞的，因為它把所有疑問一次傾倒給下游 skill，沒有做上游收斂。

````md
委派：
- 把 8 題大小不一的疑問全部交給 `/clarify`
````

# Rule 3 - 低風險未定細節應保留在 spec 中，而不是為問而問

- Level: `MUST`
- 若整份 spec 的主要故事、需求歸戶與驗收邏輯已成立，但仍有少數局部未定細節，應優先在 spec 中使用 `NEEDS CLARIFICATION` 或假設揭露，而不是新增一輪 clarify。
- 只有在未定細節已影響主要流程、正式需求邏輯或成功標準時，才應升級回 clarify。
- 不可為了追求文件表面完整，就對每個小缺口都發起訪談。

## Good Example

- 這個例子是好的，因為它把不阻塞主流程的細節保留在 spec，而不是過度追問。

````md
- **NFR-004**: 系統 MUST 在首頁載入時提供可理解的進度回饋 [NEEDS CLARIFICATION: 尚未指定是骨架屏、進度條或其他呈現方式]
````

## Bad Example

- 這個例子是壞的，因為它把本可留在 spec 的局部細節也升級為使用者訪談。

````md
缺口：
- 載入提示是骨架屏還是進度條

決策：
- 暫停 spec，立刻進 `/clarify`
````

# Rule 4 - 委派 clarify 時必須遵守下游 skill 的 session 預算

- Level: `SHOULD`
- `specify` 在委派 `/clarify` 時，應明示本輪只處理已排序的高影響題目，避免暗示下游 skill 無限制延伸提問。
- 若先前輪次已使用部分 clarify 題數，應在本輪委派時保留剩餘預算，不可假設下游 skill 仍能無上限追問。
- 若剩餘風險已可接受，應優先讓 spec 繼續，而不是耗盡 clarify 額度追求完美資訊。

## Good Example

- 這個例子是好的，因為它把本輪範圍與剩餘預算意識一起交代清楚。

````md
呼叫 `/clarify`：
- 本輪只處理故事切分邊界與成功標準兩題
- 其餘低風險細節保留在 spec 中
````

## Bad Example

- 這個例子是壞的，因為它把 clarify 視為無限制問卷，沒有預算意識。

````md
呼叫 `/clarify`：
- 只要還有任何模糊處，就一直問到完全沒有問題為止
````
