# Rule 1 - 可合理歸屬單一故事的 FR / NFR 必須直接掛在該故事底下

- Level: `MUST`
- 若某條 FR 或 NFR 主要服務單一使用者故事的成立、驗收或體驗，必須直接列在該故事底下，不可散落到故事外的總表。
- 歸戶時應優先判斷這條需求是在支撐哪一段使用者價值，而不是先依需求種類把所有 FR 集中、再把所有 NFR 集中。
- 若同一故事目前沒有專屬 NFR，可以不硬湊；但不可因為方便整理，就把明顯屬於該故事的 NFR 留在全域區。

## Good Example

- 這個例子是好的，因為瀏覽相關的 FR / NFR 都直接掛在「在首頁瀏覽日期相簿」底下。

````md
### 使用者故事 2 - 在首頁瀏覽日期相簿 (Priority: P2)

**功能需求（FR）**:
- **FR-005**: 系統 MUST 在首頁依日期由新到舊顯示所有日期相簿。
- **FR-006**: 系統 MUST 在每個日期相簿中以平鋪式預覽呈現照片。

**非功能需求（NFR）**:
- **NFR-001**: 首頁載入包含最多 200 張可見照片時，95% 的情況必須在 2 秒內完成可瀏覽畫面呈現。
````

## Bad Example

- 這個例子是壞的，因為它把明顯屬於單一故事的需求留在故事外，削弱故事與需求的階層關係。

````md
### 使用者故事 2 - 在首頁瀏覽日期相簿 (Priority: P2)

**驗收情境**:
1. **Given** ...

## 需求

### 功能需求
- **FR-005**: 系統 MUST 在首頁依日期由新到舊顯示所有日期相簿。

### 非功能需求
- **NFR-001**: 首頁載入包含最多 200 張可見照片時，95% 的情況必須在 2 秒內完成可瀏覽畫面呈現。
````

# Rule 2 - 全域需求只保留跨越多個故事或無法合理歸屬單一故事的需求

- Level: `MUST`
- `全域需求` 只應保留會同時約束多個使用者故事、或本質上無法合理指派給單一故事的 FR / NFR。
- 若一條需求只是被多個故事間接使用，但最主要仍服務其中一個故事，應優先歸到那個故事，不要過度擴張全域需求。
- 全域需求段落的存在是例外處理，不是預設集散地。

## Good Example

- 這個例子是好的，因為「相簿不得巢狀」會同時影響整理、瀏覽與排序，所以保留在全域需求。

````md
## 需求 *(必填)*

### 全域需求

#### 功能需求
- **FR-003**: 系統 MUST 將所有相簿維持為單一層級的頂層相簿，且不得出現相簿巢狀結構。
````

## Bad Example

- 這個例子是壞的，因為它把明明只跟拖放排序有關的需求放進全域需求，造成歸戶失真。

````md
### 全域需求

#### 功能需求
- **FR-009**: 系統 MUST 防止拖放排序操作改變照片所屬的日期相簿。
````

# Rule 3 - 需求歸戶後不得重複列在多個位置

- Level: `SHOULD`
- 同一條 FR 或 NFR 歸戶後，應只出現在一個最合適的位置，不應同時複製到故事區與全域需求區。
- 若同一概念真的需要在多個地方被提到，故事區應保留正式需求陳述，其他位置只保留敘述性說明，不重複編號條目。
- 需求編號應維持唯一，避免一條需求在多處出現不同版本的敘述。

## Good Example

- 這個例子是好的，因為正式需求只出現在一處，其他地方若有提及也只是說明脈絡。

````md
### 使用者故事 3 - 透過拖放調整照片順序 (Priority: P3)

**功能需求（FR）**:
- **FR-009**: 系統 MUST 防止拖放排序操作改變照片所屬的日期相簿。

### 邊界情況
- 當使用者嘗試把照片拖曳到另一個日期相簿時，系統仍須保留原本日期分組。
````

## Bad Example

- 這個例子是壞的，因為同一條需求被正式重複列在故事區與全域需求區。

````md
### 使用者故事 3 - 透過拖放調整照片順序 (Priority: P3)

**功能需求（FR）**:
- **FR-009**: 系統 MUST 防止拖放排序操作改變照片所屬的日期相簿。

### 全域需求

#### 功能需求
- **FR-009**: 系統 MUST 防止拖放排序操作改變照片所屬的日期相簿。
````

# Rule 4 - 局部缺口若不阻塞整份 spec，應標記 NEEDS CLARIFICATION 而非憑空補完

- Level: `SHOULD`
- 若某條需求的存在已可確認，但具體做法、量化門檻或適用範圍仍未拍板，且該缺口不足以阻塞整份 spec，應使用 `NEEDS CLARIFICATION` 標記保留缺口。
- 只有在缺口會直接改變故事切分、需求歸戶、主要流程或驗收標準時，才應優先回到 `/clarify`。
- 不可為了讓文件看起來完整，就替使用者發明尚未確認的需求細節。

## Good Example

- 這個例子是好的，因為它保留未確認的細節，但沒有偽裝成已定案需求。

````md
- **NFR-004**: 系統 MUST 在首頁載入時提供可理解的進度回饋 [NEEDS CLARIFICATION: 尚未指定是骨架屏、進度條或其他呈現方式]
````

## Bad Example

- 這個例子是壞的，因為它直接替使用者決定了尚未確認的細節。

````md
- **NFR-004**: 系統 MUST 以藍色線性進度條顯示首頁載入進度。
````
