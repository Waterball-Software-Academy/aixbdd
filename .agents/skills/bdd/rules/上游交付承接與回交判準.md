# Rule 1 - 只承接介面 feature 與雙層 DSL 作為上游單一溯源

- Level: `MUST`
- `/bdd` 開始前，必須先確認本輪已有使用者指定的介面 `feature file` 或其明確區塊、同模組 `dsl.md`，以及該 feature 實際使用的介面根共用 `dsl.md` rows。
- 若只拿到 acceptance Gherkin、需求敘述或零散實作想法，而沒有介面 feature 與其所需的雙層 DSL，不應由 `/bdd` 自行補成規格。
- `feature file` 承接行為邊界；模組 DSL 與實際使用的介面根共用 rows 一起承接步驟詞彙、參數與落地語意。其按需查找與專案投影方式由 `模組化Truth按需承接與Symlink判準.md` 把關。

## Good Example

- 這個例子是好的，因為它在開始前先確認 `/dsl-refine` 的正式交付物都已具備。

```md
已知輸入：
- `features/frontend/三連猜/對戰頁三連猜選擇與一次出手.feature`
- `features/frontend/三連猜/dsl.md`
- `features/frontend/dsl.md`

處理：
- `/bdd red` 承接 feature、完整模組 DSL，以及 feature 實際使用的根共用 rows
- 依其行為邊界與唯一 DSL 詞彙開始建立 focused failure
```

## Bad Example

- 這個例子是壞的，因為它缺少同模組 DSL，卻仍由 `/bdd` 猜測落地語意。

```md
已知輸入：
- `features/frontend/三連猜/對戰頁三連猜選擇與一次出手.feature`
- 只有 `features/frontend/dsl.md`

處理：
- `/bdd` 跳過同模組 `features/frontend/三連猜/dsl.md`
- 直接從根共用 DSL 猜測所有 step 的落地語意
```

# Rule 2 - 使用者指定範疇必須落在單一介面 `feature file` 或其明確區塊

- Level: `MUST`
- `/bdd` 的工作範疇必須收斂到單一介面 `feature file`，或該檔內可明確指出的 `Rule`、`Example`、scenario family 或等價區塊。
- 若範疇跨多個介面、跨多個不相干 `feature files`，或只以模糊能力名稱描述而無法穩定對應到具體區塊，應先澄清，不直接開始實作。
- 同一次 invocation 雖可 sequentially 推進多個 slices，但這些 slices 都必須屬於同一個已指定範疇。

## Good Example

- 這個例子是好的，因為它把 scope 鎖在單一介面 feature 的明確區塊內。

```md
本輪範疇：
- `features/backend/三連猜/三連猜一次出手與換手.feature`
- 僅限「一次出手成功提交」相關的 Rule 與 Examples

處理：
- `/bdd green` 只在這個區塊內依序處理待轉綠的 slices
```

## Bad Example

- 這個例子是壞的，因為它讓 scope 漂到多個介面與多個未對齊的規格。

```md
本輪範疇：
- 前端選擇
- 後端換手
- 如果順便做到 acceptance 也可以

處理：
- `/bdd refactor` 同時跨三份不同層級的 feature 思考與改碼
```

# Rule 3 - 發現規格缺口時，必須先分辨是澄清缺口還是上游交付缺口

- Level: `MUST`
- 若缺口是使用者沒有說清楚本輪範疇、目標入口或要處理哪個區塊，屬於可由 `/clarify` 收斂的澄清缺口。
- 若缺口來自 `feature file`、模組 DSL 或介面根共用 DSL 的邊界不清、詞彙缺失、驗收結果矛盾或合併後無法唯一落地，屬於上游交付缺口，應回交 `/dsl-refine` 或使用者指定的上游流程。
- 不可把上游交付缺口偽裝成下游實作細節，直接在 step definitions、helper 或產品碼中自行吸收。

## Good Example

- 這個例子是好的，因為它分清楚什麼該問使用者，什麼該回交上游。

```md
觀察：
- 使用者只說「先做前端」：這是範疇不清，先 `/clarify`
- 同一步驟在模組 DSL 與根共用 DSL 合併後有兩個定義：這是上游交付缺口，回交 `/dsl-refine`
```

## Bad Example

- 這個例子是壞的，因為它把規格問題偷偷下沉到實作層處理。

```md
觀察：
- `feature file` 的 Then 描述與模組 DSL 的權威狀態定義不一致

處理：
- 不停下
- 直接在 assertion helper 中選一個自己覺得合理的版本實作
```

# Rule 4 - 不可自行改寫上游規格來換取下游進度

- Level: `MUST`
- `/bdd` 可以回報上游規格的缺口、矛盾與阻塞，但不得自行改寫 `feature file`、模組 DSL 或介面根共用 DSL 來讓本輪開工。
- 即使只是 wording 調整，只要會影響行為邊界、參數語意、權威狀態或 DSL 唯一落地性，都應視為上游修改。
- 只有使用者明確要求切回上游流程，或先完成上游 skill 的修訂後，`/bdd` 才可重新承接更新後的交付物。

## Good Example

- 這個例子是好的，因為它寧可停下，也不侵入上游職責。

```md
觀察：
- 模組 DSL 與根共用 DSL 都缺少「玩家提交三個猜測」這個 When 的參數語意

處理：
- 回報缺口
- 停止 `/bdd red`
- 請使用者回到 `/dsl-refine` 補齊後再繼續
```

## Bad Example

- 這個例子是壞的，因為它為了順利實作，直接修改了上游規格來源。

```md
觀察：
- `feature file` 的 Given 寫法過於含糊

處理：
- `/bdd` 直接打開 feature 檔補寫更細的前置敘述
- 接著繼續寫 step definitions
```
