# Rule 1 - 開始實作前必須先盤點專案現有測試入口與 BDD 落點

- Level: `MUST`
- 在 `/bdd` 進入 `red`、`green` 或 `refactor` 前，必須先確認專案現有的 `feature` 目錄、step definitions、support files、hooks、fixtures、產品碼落點與測試啟動方式。
- 若專案已有既定目錄結構、命名規約或 runner，應優先沿用，不可無故另起一套平行結構。
- 盤點的目的，是讓本輪 scope 落到既有測試與產品碼真實入口，而不是從規格層猜測檔案應該放哪裡。

## Good Example

- 這個例子是好的，因為它先理解現有結構，再決定這輪應在哪裡增修。

```md
盤點結果：
- `frontend/features/steps/` 已存在
- 既有 runner 支援 `--name` focused rerun
- 共用 helper 在 `frontend/features/steps/shared/`

決策：
- 新 step 與 helper 都沿用既有樹
- 不另開 `bdd/steps/` 平行目錄
```

## Bad Example

- 這個例子是壞的，因為它沒看現況，就在 repo 內再造一套測試拓樸。

```md
未盤點現況，直接新增：
- `bdd/features/`
- `bdd/step-definitions/`
- `bdd/support/`
```

# Rule 2 - 必須選出最窄且可重複的測試入口

- Level: `MUST`
- 每輪都必須先找出目前專案可用的最窄 rerun 策略，例如單一 scenario 名稱、單一 `Rule`、單一 feature 檔、單一 spec 檔或等價方式。
- 若測試入口承接模組化 truth，focused runner 的必要層級另依 `模組化Truth按需承接與Symlink判準.md`；本 Rule 只負責從專案已提供的入口選出本輪最窄範圍。
- 若 runner 本身無法精準 rerun，也必須明確記錄目前選用的最小可接受範圍與原因。
- 不可把「先跑整包比較保險」當成預設做法。

## Good Example

- 這個例子是好的，因為它先確認可以窄到什麼程度，再把該入口綁到本輪 slice。

```md
rerun 策略：
- 優先 `--name "玩家一次出手成功提交"`
- 若名稱過濾不可用，退而用單一 feature 檔

本輪測試入口：
- `npm test -- --name "玩家一次出手成功提交"`
```

## Bad Example

- 這個例子是壞的，因為它直接接受高成本、低訊號的回饋迴圈。

```md
rerun 策略：
- 每次都跑全部前端、後端與 acceptance 測試
```

# Rule 3 - Given 的前置狀態應優先沿用最快且最穩定的現有技術入口

- Level: `SHOULD`
- 若專案已有 API fixture、factory、seed helper、測試資料 builder、repository helper 或測試專用 service，應優先用這些入口建立 Given 狀態，而不是預設走完整 UI。
- 只有當 `feature file` 與 `dsl.md` 明確要求以 UI 層驗收 Given，或既有技術入口不足以表達需求時，才考慮在 Given 使用較慢的端到端流程。
- 此判斷會直接影響 `/bdd` 在範疇內 sequentially 推進多個 slices 時的速度與穩定度。

## Good Example

- 這個例子是好的，因為它把慢的互動留給真正的 Act，把 Given 交給更穩定入口。

```md
Given 建態：
- 用 `roomFixture.createReadyMatch()` 建立對局狀態

When 行為：
- 由 UI 或 API 執行「提交三個猜測」
```

## Bad Example

- 這個例子是壞的，因為它即使已有快速建態入口，仍把所有前置都走完整流程。

```md
Given 建態：
- 先開首頁
- 建房
- 進房
- 等待配對
- 再逐步把資料調到可測狀態
```

# Rule 4 - 新增 abstraction 前，應先確認既有 helper、fixture 與命名是否足夠承接

- Level: `SHOULD`
- 進入實作前，應先確認既有 page object、service helper、fixture、parameter type 與 assertion helper 是否已能承接本輪 slice。
- 若既有 abstraction 只差小幅擴充即可重用，應優先延伸，而不是再創新名詞或重複層。
- 只有在現有 abstraction 的責任邊界明顯不合時，才新增新的支撐層。

## Good Example

- 這個例子是好的，因為它先延伸既有支撐層，而不是平行新建一套。

```md
現況：
- 已有 `guessFixture.createRoundState()`
- 已有 `battlePage.submitGuess(values)`

決策：
- 擴充 assertion helper
- 不新增另一個 `guessDriver2`
```

## Bad Example

- 這個例子是壞的，因為它沒有評估既有資源就直接複製能力。

```md
現況：
- 已有 `battlePage.submitGuess(values)`

決策：
- 新增 `turnSubmissionPortal`
- 新增 `guessWorkflowManager`
- 新增 `roundActionDriver`
```
