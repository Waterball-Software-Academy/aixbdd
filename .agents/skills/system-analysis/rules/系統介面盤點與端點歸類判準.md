# Rule 1 - 系統介面盤點必須先從需求部位出發

- Level: `MUST`
- 盤點系統介面時，必須先從需求原文中可辨識的使用者行為、外部依賴、資料責任或運作邊界切出需求部位，再回推對應的技術端點類型。
- 不可先預設「一定會有前端、後端、資料庫」之類的固定技術清單，再反向替它們補需求理由。
- 若某個系統介面無法指出它是從需求哪一段推得，表示該介面尚未被充分論證，不應直接寫入盤點結果。

## Good Example

- 這個例子是好的，因為它先從需求中的付款、開通與查詢責任出發，再盤出對應端點。

````md
### 系統介面的盤點

1. `前端訂閱與結帳介面`
   - 端點類型：`前端端點`
   - 主要介面：方案列表頁、結帳表單、付款結果頁
   - 需求原文依據：需求要求「使用者可以瀏覽訂閱方案」、「使用信用卡付款」。

2. `第三方金流服務介面`
   - 端點類型：`金流端點`
   - 主要介面：刷卡頁、Webhook 通知
   - 需求原文依據：需求要求「使用信用卡付款」。
````

## Bad Example

- 這個例子是壞的，因為它先列技術端點，再硬湊對應說法，沒有真的從需求部位盤起來。

````md
### 系統介面的盤點

1. `前端`
   - 理由：通常系統都會有前端。

2. `後端`
   - 理由：通常系統都會有 API。

3. `資料庫`
   - 理由：感覺之後應該會需要。
````

# Rule 2 - 每個系統介面都必須交代端點類型、主要介面與需求原文依據

- Level: `MUST`
- 盤點結果中的每一個系統介面，都必須至少包含 `端點類型`、`主要介面` 與 `需求原文依據` 三個欄位。
- `端點類型` 負責說明該介面屬於前端、後端、資料庫、第三方、手機端、硬體端、雲端或其他哪一類端點。
- `主要介面` 負責交代後續分析要聚焦的入口、契約、資料責任或操作面。
- `需求原文依據` 必須引用需求中的具體句子、需求摘要，或已成形的 `FR` / `NFR` / 關鍵實體，而不是只寫抽象判斷。

## Good Example

- 這個例子是好的，因為每個欄位都完整，後續可直接接到分析規劃。

````md
1. `訂單與訂閱持久化介面`
   - 端點類型：`資料庫端點`
   - 主要介面：使用者、訂單、付款紀錄、訂閱狀態與重試資料欄位
   - 需求原文依據：需求要求「後台查得到訂單與付款狀態」以及「付款成功後立即開通會員權限」。
````

## Bad Example

- 這個例子是壞的，因為它只有名稱，沒有揭露後續分析所需的核心欄位。

````md
1. `資料庫`
````

# Rule 3 - 只有在分析責任邊界獨立時才拆成獨立系統介面

- Level: `SHOULD`
- 若多個需求部位雖然都落在同一類技術端點，但它們的分析責任、相依關係或委派對象明顯不同，應拆成不同系統介面。
- 若多個需求部位會由同一組分析視角、同一份契約或同一類 skill 一起處理，則應優先合併，避免把盤點切得過碎。
- 不應因為某端點底下存在多條 API、數個頁面或數張資料表，就自動把它們全部拆成獨立系統介面。

## Good Example

- 這個例子是好的，因為它只在責任邊界真的不同時才分開盤點。

````md
1. `後端訂單與訂閱 API 介面`
   - 端點類型：`後端端點`
   - 主要介面：建立訂單、接收付款結果、開通訂閱

2. `訂單與訂閱持久化介面`
   - 端點類型：`資料庫端點`
   - 主要介面：訂單、付款與訂閱狀態持久化
````

## Bad Example

- 這個例子是壞的，因為它只是把同一個後端責任切得過碎，卻沒有提供新的分析價值。

````md
1. `建立訂單 API`
2. `查詢訂單 API`
3. `Webhook API`
4. `付款狀態 API`
````
