# Rule 1 - Wave 順序必須反映需求依賴與資訊供給順序

- Level: `MUST`
- `Wave` 的先後順序，必須反映後續分析是否依賴前一波先收斂出的資訊，而不是只看端點名稱是否好分組。
- 若某個端點的分析必須先知道另一個端點的使用者流程、第三方限制、輸入輸出契約或資料邊界，則它應排在較後的 `Wave`。
- `Wave` 的作用是表達「什麼分析應先做、什麼分析應後做」，不是把所有端點平均分配。

## Good Example

- 這個例子是好的，因為它先分析需求入口與外部限制，再分析依賴它們的內部設計。

````md
#### Wave 1

- 平行分析介面：
  - `前端訂閱與結帳介面`
  - `第三方金流服務介面`
- 安排理由：先收斂使用者流程與第三方限制，供後端與資料庫後續承接。

#### Wave 2

- 平行分析介面：
  - `後端訂單與訂閱 API 介面`
  - `訂單與訂閱持久化介面`
- 安排理由：後端與資料庫分析依賴前一波先收斂出的 UI 流程與金流契約。
````

## Bad Example

- 這個例子是壞的，因為它只是把端點平均拆開，沒有表達真正的依賴順序。

````md
#### Wave 1

- 平行分析介面：
  - `後端`
  - `資料庫`

#### Wave 2

- 平行分析介面：
  - `前端`
  - `第三方`
````

# Rule 2 - 同一個 Wave 只放可平行分析的介面

- Level: `MUST`
- 只有在兩個以上系統介面的分析工作，彼此不需要等待對方先產出具體結論時，才可放在同一個 `Wave` 中平行進行。
- 若某介面的分析需要先知道另一介面的分析結果，則必須拆到後續 `Wave`，不可因為它們同屬不同端點就強行並排。
- 平行的判斷依據是分析相依性，而不是執行者數量或主觀上的「好像可以一起做」。

## Good Example

- 這個例子是好的，因為兩個端點都能先各自收斂自己的輸入材料，再把結果交給後續分析。

````md
#### Wave 1

- 平行分析介面：
  - `前端照片工作區介面`
  - `第三方金流服務介面`
````

## Bad Example

- 這個例子是壞的，因為資料庫分析其實還在等後端契約定義，卻被放在同一波平行處理。

````md
#### Wave 1

- 平行分析介面：
  - `後端訂單與訂閱 API 介面`
  - `訂單與訂閱持久化介面`
- 安排理由：先一起做比較快。
````

# Rule 3 - 每個 Wave 都應同時交代分析重點與安排理由

- Level: `SHOULD`
- `Wave` 不應只列出介面名稱，還應交代這一波實際要收斂的分析重點，以及為什麼這些介面被放在同一波。
- `分析重點` 負責揭露每個端點在這一波的工作焦點；`安排理由` 則負責解釋依賴順序、平行性與 handoff 邏輯。
- 若缺少這兩類資訊，後續接手的子 skill 或 sub-agent 容易不知道各波段真正的目標與界線。

## Good Example

- 這個例子是好的，因為它不只列介面，還把每波要做什麼與為什麼這樣排一起說清楚。

````md
#### Wave 1

- 平行分析介面：
  - `前端訂閱與結帳介面`
  - `第三方金流服務介面`
- 分析重點：
  - 前端先分析 UI/UX 流程、狀態與錯誤回饋。
  - 金流端先分析第三方文件、Webhook 規格與整合限制。
- 安排理由：兩者都能先獨立收斂，且會直接影響下一波後端與資料庫分析。
````

## Bad Example

- 這個例子是壞的，因為它只有清單，沒有揭露分析焦點與依賴理由。

````md
#### Wave 1

- 平行分析介面：
  - `前端`
  - `金流`
````

# Rule 4 - plan artifact 只規劃分析流程，不提前寫出分析結果

- Level: `MUST`
- `分析流程規劃` 區塊的責任，是盤點系統介面並安排後續分析順序、分波與焦點，不是直接產出各介面的實際分析結論。
- 若某段內容已經開始定義最終 API 欄位、資料表 schema、第三方參數對應或具體 UI 元件設計，表示它已超出本 artifact 的規劃層級。
- 在這個 artifact 中，應停留在「哪些介面要分析、為何先後、每波聚焦什麼」的粒度。

## Good Example

- 這個例子是好的，因為它交代的是後續分析任務，而不是已完成的設計結果。

````md
#### Wave 2

- 平行分析介面：
  - `後端訂單與訂閱 API 介面`
  - `訂單與訂閱持久化介面`
- 分析重點：
  - 後端分析聚焦建立訂單、接收 webhook 與開通訂閱的責任邊界。
  - 資料庫分析聚焦訂單生命週期、付款狀態與訂閱狀態的持久化需求。
````

## Bad Example

- 這個例子是壞的，因為它已經把具體設計答案先寫進規劃區塊。

````md
#### Wave 2

- 後端 API 必須有 `POST /checkout`、`POST /webhook` 與 `GET /subscription-status`。
- `orders` 資料表必須包含 `status`、`provider_ref` 與 `retry_count` 欄位。
````
